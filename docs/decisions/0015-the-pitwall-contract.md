# 0015: The pitwall contract

## Status

Accepted (user, 2026-11-02). Replaces the previous `docs/architecture.md`; amends ADRs 0008 (config and the new priors store), 0011 and 0014 (calculators, analyses, simulators, presentation in displays), 0013 (UI state, decisions). The situations spec of 2026-10-30 and the SP4a spec and plan are superseded (SP4a is re-specced after the migration).

## Context

Live testing and nine review waves (2026-10-30/31) showed one root cause behind most bugs: every module re-derived the same situation (pit, garage, safety car, finish, retirement) from the game's raw statuses with its own local rule, and each fix in one module broke another. The first slice of a situation tracker made it worse in one respect: it rewrote history (formation discard, start re-stamp, a "shared-moment" rule) under one boolean flag, and the rules that grew around it were written only in specs and code comments. The survey `docs/history/specs/2026-11-02-race-state-machine/01-current-architecture.md` lists 12 places that decided situations outside the tracker and 7 rules changed without being written down. Workers under pressure took the shortest local path because nothing in their context forbade it.

## Decision

`docs/architecture.md` is the contract: numbered clauses with enforcement tags and a glossary, imported into every agent's context by CLAUDE.md. The reasons, per clause or group:

- **C0.** A contract that bends per task stops being one. Changing it first and adapting the code before anything else avoids building twice on a contract that is about to change; a gap stops the whole sub-project because work on a changing contract is work done twice (user).
- **Glossary.** Words like "machine", "signal" and "fact" were read differently by different agents; one meaning each removes the room for a local rule.
- **C1–C4.** Unchanged rules of the foundation (ADRs 0001, 0003), kept because the purity of engine and analysis is what makes determinism and incremental = from scratch testable.
- **C1a, C8 (realism, freshness), C37 (feed health).** Rules of the previous architecture document carried over (ADR 0009, realism mode, the UI's staleness).
- **C5, C6.** The game's format is the most likely thing to change (F1 26) or to multiply (another game); confining it to an adapter keeps everything above it untouched.
- **C7–C11.** The old step order carried meaning only in comments, and modules coupled through each other's open state (`pit-stops` setting the lap cursor's out lap). Fixed steps with no coupling inside a step make order irrelevant and testable by shuffling. The clock detects an online pause from the game's pause signal, which it reads from the frame because it runs before step 1 (M1 review, user). Step 1 writes the signals, so it may read them to shape the values it writes (realism, placing the player and the teammate, keeping only this session's forecast); it decides no situation (user, 2026-11-04).
- **C12, C13.** Only a closed list enforced by types makes a local situation rule a compile error instead of a review finding.
- **C14–C17.** The weekend phase decides which rules apply; sub-machines are shared only where recordings show the same signals in two phases, so shared code never hides a phase difference. One scope per sub-machine (user): membership maps a sub-machine to one span per scope at a frame, so a sub-machine with two scopes would have no single answer. The scope is declared in `domain` beside the span types, because readers need it (the projection's membership, analyses, displays) and may not reach the adapter (user, 2026-11-03). Registration by convention makes adding or moving a sub-machine cheap (user). Car activity rests in `not competing` while a car does not compete, so its spans have no gap (user, 2026-11-04). Who drives a car is a sub-machine, not a value: the game reports it as a signal, and online the AI takes over a human who drops out, so a car's frames split into AI and human spans that driver profiles and the noise model follow (user, 2026-11-11).
- **C18, C19.** The game's signals are noisy and out of step; opening on the earliest signal and recording an unconfirmed span as such keeps the log truthful without ever withdrawing a fact.
- **C20.** Two doors (open spans in the view, closed spans in the projection) are enough for every reader and leave no third way to re-derive.
- **C21–C26.** History is never edited (user): an immutable log and references instead of updates. Membership is computed by the projection from frame numbers, not stamped at recording (user, 2026-11-03): a stamp gave a late fact the spans open when it was recorded, not those of the frame it describes (a lap provisional on green, an SC deployed, the lap confirmed under the SC; a drive-through served up to 10 s after the pit exit). Frame numbers, not race-clock times, because several frames share one time, which caused the old shared-moment bugs; the shared-moment rule stays gone. Fact ids skip voided facts, so a run with a rewind gives the same ids as one without (C33; M1 review, user).
- **C27, C27a.** A flashback means the undone time never happened (user); a void fact expresses that by appending. Decisions are voided too, because they rested on facts that no longer happened (user). Nothing else records the flashback: no timeline that exists contains one, so no analysis has a reason to read it (user).
- **C28, C29, C34.** One module applies voids and formation hiding (by the frame a fact describes), so no reader can get them wrong; storage keeps everything, and nothing reads hidden facts until a reader is designed (user). Formation hiding is for what the game produced during the formation lap, which is not race data. A decision is the engineer's input, and committing a plan or a calibration on the grid or in the formation lap is normal, so formation never hides it; this replaces the ruling of 2026-11-04 that hid it (user, 2026-11-06).
- **C30–C33.** Only state derived from the projection must react to a rewind; the accumulator is the one fenced exception, allowed only when counted work proves from-scratch cost grows with the race (a deterministic count, not a timer, so the proof cannot flake or depend on the machine; at least 5 times from lap 7 to lap 70, averaged over each lap's frames, so linear growth with fixed overhead still qualifies; user), because state kept between frames is where incremental readers went wrong. Insights are recomputed after a rewind because the engineer never saw them in the correct timeline (user).
- **C35–C38.** One continuous race clock; a fall is carried over instead of re-timing facts; determinism makes every run reproducible from its recording and sidecars.
- **C39–C49.** The view is the only input of a unit, change tags come from registries, and a guarded view in tests catches undeclared reads; judgements live in calculators and analyses so two displays never disagree. Sub-machine and recorder thresholds are constants, not config: they change the log, so they belong to the rules version, and they have no view to read config from (user, 2026-11-04).
- **C50, C51.** Simulators stay plain functions so a model can be swapped or ported; jobs keep expensive work off the frame path.
- **C52.** Insights come from analyses; the scheduler raises only `system` insights, the bridge only `feed` (feed health) and `system` insights, so feed alarms can be muted on their own (user, 2026-11-04, final migration review). There is no flashback insight (C27).
- **C53–C57.** Topics are the seam to the UI; core topics publish facts and spans as they are, analysis topics publish judgements, and no signal crosses. `bindLive` publishes a part of the live state without a calculator in between: the hub reads it when it sends and copies only what the topic selects; a calculator holding the cars as its output would have to copy them every frame, since kept outputs never change (C30; M1 acceptance slowdown, user). The bridge's user state (UI state, calibration) is published as core topics by the module that owns it: it is not engine output, so no binding fits it. A feed's calibration choice is the run's input, like the track file, not a judgement: an analysis would only copy it, so its feed's pipeline publishes it as a core topic (user, 2026-11-06).
- **C58–C63, C62a.** All I/O in the bridge; recordings are the truth and storage a rebuildable cache; the rules version is a hash of the source of every module that can change the log, computed rather than kept by hand, because hand-kept versions missed shared helpers, frame assembly, the runner and decoding, and a computed hash can be neither forgotten nor gamed; the price is that any edit there rebuilds stored sessions (user); it rebuilds stale sessions, starting with the newest stored weekend, the only one known at bridge start; the priors store holds the aggregates of the user's calibration sets as a versioned cache. Calibration is the engineer's tool, never a hard-coded rule: which data counts changes as the car and the driver change, so the user picks the sources and overrides the numbers, in garage time between live actions, with or without a session loaded (user, 2026-11-06). A set belongs to one track (pace, degradation, wear and pit loss depend on it). The run starts on a preselected set at once, since frames cannot wait for an answer; a different pick is a recorded decision so a replay switches at the same frame. The values are view input like config and the track file, not facts: a decision names the snapshot it chose and the sidecar holds the snapshot, so the log stays free of unit outputs (C23) and a replay sees the values that were chosen, whatever the set became later (user, 2026-11-06). An edit of the set a run uses reaches the running session as a calibration-chosen decision, so the engineer can correct a number mid-session and a replay switches at the same frame as the live run; no accumulator holds priors, so a switch rebuilds nothing (user, 2026-11-06). The store is also rewritten after a rebuild while a session runs, as a rebuilt source session changes its entries; the running session computes on its snapshots and is not touched (user, 2026-11-06). Which stints are suggested and how a source is compared with its set are judgements, so the units declare them, not the bridge (C43). A car is matched across a weekend's sessions by team and race number: car slots change between sessions (weekend 3895515742: car 1 is Alonso in qualifying, Stroll in the race), online humans have no game driver id (255), and team and race number are unique in every session of every recording (2026-11-04); pitwall tracks cars as the game names them, not who plays them (user); the one exception is the driver profile (C62c): how consistent a human drives belongs to the person, not the car or the track, so it is learned across every session and track the person drove; the game has no id for an online human, so the user confirms a person's link once by name and race number (user, 2026-11-10). Every car's identity is stored now, so later units can match rivals across sessions (user, 2026-11-04). Storage is keyed by the feed's player car, so two feeds of one session are stored side by side (C1a; user, 2026-11-04).
- **C62b.** Track data (outline, turns, braking zones, per-track defaults) is reference data that never changes during a season; computing it live from positions would need frame data in the log or in accumulators, which C31 and C32 forbid, and it would be missing exactly when it is needed, on the first laps (user, 2026-11-05). It is made outside pitwall, so the rules version stays stable when a file improves; units need it from the first frame; per-track defaults belong with the track, not in a unit's config; the sidecar keeps a replay deterministic when a file changes later. A session without a valid file writes a not-applicable sidecar, so committing a file for its track later does not change its replay (user, 2026-11-06).
- **C62c.** A human driver's consistency and mistakes decide whether a plan survives the race, and the league's drivers differ widely (one consistent, one erratic; AI drivers very consistent); a calibration set belongs to one track, so a person's history would split over 24 tracks with about one race each per season (user, 2026-11-10). The profile is curated like a calibration set and handed to a run as a fixed snapshot in a sidecar, so a replay sees the values that were used.
- **C64–C71.** The UI rules of SP2 and ADRs 0012–0014, plus presentation tables so layouts can follow the situation without displays judging anything (user).
- **C72–C77.** Every action is a command; persistent changes go through the bridge; a manual layout choice is never overridden (user); decisions are recorded facts so replays reproduce them (user); pitwall never controls the game.
- **C78–C83.** Ownership and the two-phase workflow keep parallel workers from colliding; briefs cite clauses so every change is checked against the contract. A minor change skips the two phases: two agents for a header word or a literal port cost time and agents and test nothing a separate test agent would catch, and its related tests cover it where the whole suite (about 15 minutes) adds nothing (user, 2026-11-06).
- **C84–C88.** Tests target one behaviour on small segments; every transition is tested by tables, completeness and one property per sub-machine; workers run related tests, the supervisor the full suite per merge (user).
- **C89.** Open review questions looped for eight waves; asking only whether the contract was violated converges and points every finding at a clause (user).
- **C90.** A change to any module that can change the log alters stored history; computing the rules version from their source makes the rebuild automatic (user).

## Consequences

- The existing code violates many clauses (survey §7, §8). A migration plan adapts it before any other code is written (C0); it replaces situations plan Tasks 3–9 and precedes SP4a.
- Enforcement that does not exist yet (the signals module, the projection, the void fact, the machine registry, the guarded view, the shuffle test, generic completeness tests, `pitwall scan-situations`, the version-bump test, the priors store) is built by the migration: `docs/history/specs/2026-11-02-race-state-machine/03-traceability.md` §5.
- Every brief names the clauses it touches; every review asks one question (C89).
