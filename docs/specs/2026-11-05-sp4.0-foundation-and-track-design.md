# SP4.0: foundation and track

Status: design approved in the SP4 brainstorm, 2026-11-05 (sections 1 to 3, answers A11 and A15 to A19 in `00-carry-over.md` §9). The first of the four SP4 sections (`01-sp4-sections.md`).

## 1. Goal

Every track of the 2025 season has a committed track file, and pitwall reads it as `view.track`. On that base, three features exist afterwards that do not exist now:

- a **track map** with the outline, official turn labels, every car, marshal-zone flags, the blue flag and incident markers;
- **official turns in the incident feed** (`T6a` instead of `S2`);
- a **talk indicator** in the top bar: whether now is a good moment to radio our driver (not inside or just before a braking zone).

Nothing is computed from positions live: track data is reference data, made once per track outside pitwall (A3).

**Not in 4.0:** the cadence `ourCrossing`, the ghost marker and the rejoin ghost on the map (4.2, with `rejoin`); the source badge (4.1); pit exit on the map (4.2, if `rejoin` needs it); reverse layouts (no file); measured track data from our recordings (a later sub-project with the priors store).

## 3. The track file

### 3.1 Type

`TrackData` and `TrackFile` in `packages/domain/src/track-file.ts` (supervisor). Every lap position is a **lap fraction** in `[0, 1)`: the game's track length and coordinate frame differ from the real track's, so a fraction times the session's `trackLengthM` is the game's lap distance. Every part is `Known`, so a file can carry only what exists for its track.

```ts
export type LapFraction = number; // [0, 1)
export type MapPoint = { x: number; y: number }; // unit square, y down, rotated for display

export type TrackTurn = { number: number; letter?: string; label: string; apex: LapFraction };
export type BrakingZone = { start: LapFraction; end: LapFraction };
export type TrackDefault<T> = { value: T; source: string }; // source: "OpenF1, 2025 <event> R, median of n stops"

export type TrackData = {
  trackId: number;
  name: string;
  realLengthM: Known<Metres>;
  outline: Known<MapPoint[]>;          // 500 points at equal lap fractions; point i at i/500
  turns: Known<TrackTurn[]>;           // in lap order
  brakingZones: Known<BrakingZone[]>;  // in lap order, disjoint; a zone may wrap past the line (start > end)
  defaults: {
    pitLossMs: { green: Known<TrackDefault<Ms>>; vsc: Known<TrackDefault<Ms>>; sc: Known<TrackDefault<Ms>> };
    compoundOffsetsMs: Known<TrackDefault<{ soft: Ms; medium: Ms; hard: Ms }>>; // relative to medium = 0
  };
};

/** The file as committed and as the sidecar: the data plus its provenance. */
export type TrackFile = TrackData & {
  source: { generator: string; sources: string; season: number; generatedOn: string }; // sources: "OpenF1 + MultiViewer"
};
```

`view.track` is `Known<DeepReadonly<TrackData>>`: the loader drops `source`, so the generation date (a wall-clock date) never reaches the view (C35); the sidecar keeps the whole file. Every `Ms` is an integer (C4): the generator rounds each median and each ratio estimate to whole ms, and the validator rejects a non-integer. The JSON file stores `Known` values in their serialised form (`{ known: true, value, at: 0 }` or `{ known: false, reason }`).

### 3.2 Content and source

From OpenF1 (`api.openf1.org/v1`: `sessions`, `laps`, `car_data`, `location`, `pit`, `stints`, `race_control`) and the MultiViewer circuit API (`api.multiviewer.app/api/v1/circuits/<circuitKey>/2025`: `rotation`, `corners`), 2025 season, per track (user decision 2026-11-06: FastF1's source needs an F1TV account, which the user has none of). "The pole lap" is the fastest qualifying lap (`laps`, session `Qualifying`); a lap's samples are the `car_data` and `location` samples from its `date_start` to `date_start + lap_duration`, and a sample's lap distance is the speed integrated over time from the lap's start, scaled so the lap's total is `realLengthM`.

| Part | Derived from |
|---|---|
| `realLengthM` | the pole lap's `car_data` speed integrated over its time |
| `outline` | the pole lap's `location` x/y, resampled at 500 equal fractions of its path length starting at the lap's first sample (the line), rotated by MultiViewer's `rotation`, normalised to the unit square |
| `turns` | MultiViewer `corners`: `number`, `letter`, label `T<number><letter>`; apex = the lap fraction of the pole lap's `location` sample nearest the corner's `trackPosition` |
| `brakingZones` | `car_data` `brake` (0 or 100) on the fastest qualifying laps of the top five: per zone the median onset and release lap distance, a zone kept when a majority of the laps brake there, zones shorter than 20 m dropped, zones closer than 30 m merged (samples are 4–5 Hz, so onsets are accurate to about 20 m) |
| `pitLossMs.green` | 2025 race stops (`pit`) whose in-lap (the lap before the `is_pit_out_lap` lap) and out-lap overlap no `race_control` SafetyCar or red-flag period and no yellow flag: in-lap + out-lap − 2 × the car's median racing lap of the 3 laps before (TUM's definition), median over stops |
| `pitLossMs.vsc`, `.sc` | the same over stops whose in-lap, out-lap and 3 reference laps lie in a VSC or SC period (from `race_control` SafetyCar deployed/ending messages) if there are at least 2 such stops; else 0.55 × green (VSC) and 0.45 × green (SC), source "ratio of green, pitwall estimate" |
| `compoundOffsetsMs` | 2025 race `stints` × `laps`: median fuel-corrected racing lap per compound (γ = 30 ms/kg, 1.8 kg/lap; lap 1, in-laps, out-laps and laps in an SC, VSC or red-flag period excluded), relative to medium; unknown unless soft, medium and hard all appear |

A track whose data lacks a part has that part `unknown('notReceived')`. Reverse layouts (ids 39, 40, 41) get no file.

The defaults are real-F1 values, not the game's (A15). They are defaults only: `pit-loss` (4.1) replaces them by this session's measured stops, and a later sub-project by stored data.

**Licence (risk):** OpenF1 serves F1's live-timing data, which belongs to F1; the MultiViewer API publishes no licence. pitwall is not released (scope answer, research 08), so committing derived numbers is accepted. Revisit before any release.

### 3.3 Production: the aux repo

A new repo `~/dev/personal/pitwall-trackdata` (memory rule "keep aux tools separate"): Python 3; every API response is cached in the repo's gitignored `cache/`, and requests stay within OpenF1's rate limit.

- `generate --season 2025 [--track <trackId>] --out <dir>` writes `<trackId>.json` per track of the 2025 calendar, with the mapping from F1 event to game track id in one table (`tracks.py`).
- Its own tests: the TUM pit-loss arithmetic on a hand-made stint, braking-zone merging, resampling, and the JSON shape against a copy of the `TrackFile` schema.
- It imports nothing from pitwall; pitwall imports nothing from it. The supervisor copies the files into `data/tracks/` and commits them (`build: track files for the 2025 season`).

### 3.4 In pitwall

- **Validation test** (`packages/domain/test/track-files.test.ts`): every file in `data/tracks/` parses against `TrackFile` (a hand-written validator next to the type, also used by the bridge loader), its name is its `trackId`, turns are in lap order, zones are disjoint, every fraction lies in `[0, 1)`, every `Ms` is an integer, the outline has 500 points.
- **Segment test** (`apps/bridge/test/track-files/zandvoort-against-game.test.ts`): on `race-zandvoort-full-lap` (existing segment), each Zandvoort apex lies within 60 m of a peak of our car's steering (|steer|; a fast corner has no speed minimum, run ruling 2026-11-06), and each braking zone overlaps a stretch where our car braked. It tests the file against the game, not a fact of the recording (C84).

## 4. The bridge: loading and the sidecar

- `apps/bridge/src/track-files/load.ts`: `loadTrackFile(trackId, dir): Known<TrackFile>`: reads `<dir>/<trackId>.json`, validates (the sidecar gets the whole file, `view.track` its `TrackData`, 3.1); missing → `unknown('notApplicable')`; invalid → `unknown('notApplicable')` and a line on the bridge's log (no insight, C52).
- The directory is `<repo>/data/tracks`, resolved from the bridge's package root (no new environment variable, C58: it is not a data dir).
- At session start (`session-processor`, where the config is fixed for the run) the bridge loads the file for the session's `trackId`, hands it to the scheduler input as `track`, and the recording writer writes it as `<recording>.track.json` (C59). A replay reads `<file>.track.json` if present, else loads the committed file (C62b).
- `EngineView` gains `track: Known<DeepReadonly<TrackData>>` (`packages/engine/src/calc/types.ts`, supervisor). The guarded view (C41) treats `track` like `config`: always readable, no change tag (it never changes within a run).
- Determinism (C38): the stream hash of a replay with the sidecar equals the live run's; a test replays a segment with a sidecar and with a different committed file and gets the sidecar's result.

## 5. `track-lookup`

`packages/analysis/src/shared/track-lookup.ts` (pure, no config; callers pass their thresholds):

| Function | Returns |
|---|---|
| `fractionOf(lapDistanceM, trackLengthM)` | the lap fraction, wrapped into `[0, 1)` |
| `pointAt(outline, fraction)` | the point linearly interpolated between the two neighbouring outline points (wrapping at the line) |
| `turnAt(turns, fraction, trackLengthM, snapM)` | the label of the turn whose apex is nearest, if within `snapM`, else `undefined` |
| `sectorOfDistance(lapDistanceM, sector2StartM, sector3StartM)` | 1, 2 or 3 (named apart from `incidents`' own `sectorAt` over crossings) |
| `brakingAhead(zones, fraction, trackLengthM, leadM)` | `inside`, `ahead` (a zone starts within `leadM`) or `clear` |

Tests: properties (a point at a fraction lies on the segment of its neighbours; `fractionOf` wraps; `turnAt` never returns a turn farther than `snapM`; `brakingAhead` is `inside` exactly within a zone, also across the line) plus edge cases (empty lists, a wrapping zone).

## 6. Analyses

Each analysis declares its thresholds in its own `config.ts` (C47; `track-positions` has none) and a behaviour table for every sub-machine it reads (C44); topics in `packages/contracts/src/topics/` (C53), named after the owner (C56). Our cars are `playerCar` and `teammateCar` from the live session (C1a: per feed).

### 6.1 `track-positions`

**Topic `trackPositions.geometry`** (`state`, `maxHz` 1, no params):

```ts
type TrackGeometry = {
  outline: MapPoint[];
  turns: { label: string; point: MapPoint }[];
  sectorStarts: [MapPoint, MapPoint, MapPoint];   // line, sector 2, sector 3
};
// topic value: Known<TrackGeometry>; notApplicable without a file or without an outline
```

Reads `track`, the live session's `trackLengthM`, `sector2StartM`, `sector3StartM`. Cadence `sessionChange`: the file is fixed for the run; the sector starts arrive with the first Session packet.

**Topic `trackPositions.cars`** (`state`, `maxHz` 10, no params):

```ts
type MapCar = {
  carId: CarId; code: string; teamId: number; ours: boolean;
  point: MapPoint; inPit: boolean; blueFlag: boolean;
};
type MapZone = { start: LapFraction; end: LapFraction; flag: ZoneFlagKind };  // zone-flags kinds
type TrackCars = { cars: MapCar[]; zones: MapZone[] };
// topic value: Known<TrackCars>; notApplicable without a file or without an outline
```

- `cars`: every car whose car status is competing (behaviour table over `car-status`), at `pointAt(fractionOf(lapDistanceM))`; `inPit` from `car-location` (`pitLane` → `true`, drawn hollow; `garage` → the car is left out); `blueFlag` from `car-flags` (`blue`). Realism keeps positions (they are public).
- `zones`: one per open `zone-flags` span, from its `startFraction` to the next zone's (the last to the first + 1, wrapped).

Reads: live car timing and participants, `car-status`, `car-location`, `car-flags`, `zone-flags`, `track`. Cadence `frame`: positions change on every frame, and the topic's `maxHz` caps what the map can draw (N1).

The incident markers are not `track-positions`' output: a list of what happened is built from the projection by its owner, never from another unit's current output (C45), so `incidents` publishes them (6.2).

### 6.2 `incidents` (change)

- `IncidentWhere` (domain) becomes `{ sector: Known<1 | 2 | 3>; turn: Known<string>; fraction: Known<LapFraction> }`.
- `turn` = `turnAt(..., snapM)` with `turnSnapM` in `incidents`' config (default 60, pitwall estimate); `unknown('notApplicable')` without turns in the track file, and `unknown('insufficientData')` when no apex is within `snapM` (the feed then shows the sector, D4).
- `fraction` = where the car was at the incident's time, interpolated by time between the two mini-sector crossings around it (the unit already locates the sector this way, `sectorAt` over the car's crossings); it needs only the session's track length, not the track file; `unknown('insufficientData')` without crossings around the time. `turn` is looked up from this fraction.
- `fraction` and `turn` are computed in `output`, where `sector` already is (it reads the live layout): `view.track` and the live state are neither projection nor config, so the accumulator never holds anything derived from them (C31.2).
- **Markers.** The output becomes `IncidentsOutput = { feed: IncidentEntry[]; markers: Known<MapIncident[]> }` with `MapIncident = { point: MapPoint; kind: IncidentKind }` (domain). `markers`: the major entries (`severity: 'major'`, the per-kind `<kind>Major` config, as the mockup's "major incident of the last 2 laps") whose `where.fraction` is known, while the leader is fewer than `markerLaps` laps (config, default 2, pitwall estimate) past the leader's lap at the entry (user decision 2026-11-05: leader's lap, major entries; no `markerKinds`), at `pointAt(outline, fraction)`; taken from the entries before the `feedLength` cut, so a long feed never drops a marker; computed in `output` (C31.2); `notApplicable` without a track file or without an outline.
- Topics: `incidents.feed` binds the output with `select: out => out.feed` (unchanged value); new **`incidents.markers`** (`state`, `maxHz` 1, no params) binds it with `select: out => out.markers` (C53, C55, C56).
- Readers of the output and of `IncidentWhere`: `incident-feed` (shows `turn` when known, else the sector), `race-moment` (reads `out.feed`; ignores `where`), `track-map` (the `incidents.markers` topic, 7.2). Existing tests that read the output as an array (`packages/analysis/test/incidents/*`, `apps/bridge/test/features/incidents/register.test.ts`, `race-moment`'s) are ported to `.feed`, not dropped (C82). The test phase greps all readers again.

### 6.3 `talk-window` (N9)

**Topic `talkWindow.car`** (`state`, `maxHz` 10, params `carId`; our cars only, any other car `notApplicable`):

```ts
type TalkWindow = { talk: Known<'clear' | 'busy'> };
```

- `busy` when `brakingAhead(zones, fraction, trackLengthM, speedKmh / 3.6 × leadS)` is `inside` or `ahead`; else `clear`. `leadS` in config, default 1.5 s (pitwall estimate, A17).
- Behaviour table over `car-location`: `track` → by zones; `pitLane` → `clear`; `garage` → `notApplicable`.
- `notApplicable` without a track file or without braking zones.
- Reads: live car timing (lap distance) and motion (speed), `car-location`, `track`. Cadence `frame` (lap distance changes on every frame).

## 7. UI

### 7.1 Kit: track outline canvas (supervisor)

`apps/ui/src/kit/track/TrackCanvas.svelte`: draws a closed polyline of `MapPoint`s scaled into its box with a margin; segment colouring by fraction range (for zones). Colours only through theme roles (C68).

It also lays out everything on the map, so the widget measures and computes nothing (C65; measuring lives in the kit, `kit/size/measure.ts`): it takes labels (text at a point, placed outside the bend of the outline there), dots (point, style role, size, hollow), side bars (a 3 × 12 px bar in a role, attached to a dot) and markers (point, label), and places them so that labels never overlap each other, the dots or the line and stay inside its box, and each side bar sits on the first free side of its dot. The placement is a pure function next to the component (`kit/track/layout.ts`) with its own tests (no overlap, inside the box, a bar on a free side, a stable result for the same input).

### 7.2 Widget `track-map`

`apps/ui/src/widgets/track-map/`, from the approved mockup `docs/design/2026-10-30-sp4a-displays/2-map-views.html` without the ghost (4.2): sizes 32×10 compact and 64×20 full (cells).

- Reads `trackPositions.geometry`, `trackPositions.cars` and `incidents.markers`.
- Hands `TrackCanvas` (7.1) what to draw; the canvas places it. The outline in `textFaint`; turn labels and sector labels; rivals as dots in their team colour, our cars white and larger; in-pit cars hollow; a yellow zone redraws its stretch in `flagYellow`; a car under blue gets a `flagBlue` side bar; incident markers as amber triangles labelled with the kind (kit `incidentKinds`).
- `presentation.ts` (C66): zone-flag kind → stretch colour role (`yellow` → `flagYellow`; `green`, `blue`, `noFlag`, `unknown` → none), car state → dot style. Completeness test over the zone-flag kinds.
- `notApplicable` geometry → the panel's note "no track data" (`text.ts`).
- Gallery: one case per size for the screenshot baseline, plus non-screenshot cases (no file, yellow zone, blue flag, incident). The Zandvoort outline is a copy in the widget's own `fixtures.ts` (as `timing-tower` does), never an import from `data/tracks/` or `test-support/` (C69).

### 7.3 Widget `incident-feed` (change)

Shows `where.turn` when known, else the sector as today. Gallery case with a turn.

### 7.4 Top bar segment `Talk` (shell, supervisor, delegated in two phases)

`apps/ui/src/shell/topbar/segments/Talk.svelte`: subscribes to `talkWindow.car` for the player car (through the top bar's model, C64); a dot in role `textDim` when `clear`, `warning` when `busy` (user decision 2026-11-05: colour only where it warns; the theme has no `positive` role); hidden when `notApplicable` or unknown. Wording in the top bar's text. Emphasis map `talk → role` in `emphasis/`.

### 7.5 Workbook

`track-map` joins the default `race` workbook (`apps/bridge/src/ui-state/default-workbooks/race.json`) in the side column. Data dirs that already hold a `race` workbook keep theirs; the user adds the panel with the "add panel" command of the live-polish plan (N10).

## 8. Error handling

- Missing data is `unknown(reason)`, never 0 (C3): no file or invalid file → `notApplicable`; a part missing in the file → its own `unknown` carried through.
- A car without a lap distance yet (before its first LapData) is left off the map.
- A track id the game does not list (`-1`) → no file.

## 9. Testing

- Per unit: transition and completeness tests where they apply (C87: behaviour tables, presentation tables, guarded views); builders for zone, lead, pit, garage, no-file and wrapping-zone cases; no test reads `PITWALL_DATA_DIR` (C84); tests that need a track file pass a committed fixture file (`test-support/fixtures/track-zandvoort.json`, a copy of the generated one).
