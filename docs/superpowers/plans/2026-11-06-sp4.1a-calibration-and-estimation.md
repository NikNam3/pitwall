# SP4.1a Calibration and Estimation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In this repo every task has two phases by two agents (contract C82): a test agent writes the failing tests and commits them, an implementation agent makes them pass without touching them. Supervisor steps (marked **supervisor**) commit the contract, contract-first types (C81), data files and gates, and write no logic.

**Goal:** The engineer builds per-track calibration sets from stored sessions and picks one per session; `degradation`, `tyre-life` and `pit-loss` start from it and take over from the session's laps; the stint scatter, the pit-loss table and the calibration panel show them in a new `garage` workbook.

**Architecture:** Calibration sets are user-authored files the bridge owns; estimation units declare pure `aggregate`, `residual` and `candidate` functions (`definePriors`) that the bridge's priors store runs over stored projections and caches. Calibration values are view input, like config and the track file: the bridge hands the run its priors snapshots (`RunPriors`: the session-start snapshot and every picked one, by fingerprint, also the priors sidecar), and the scheduler picks `view.priors` from the projection with `priorsOf` (the newest `calibrationChosen` decision's snapshot, else the start one), as it takes the situation from `situationOf`. A pick is the first decision kind: it names the set and the snapshot, never the values (C76, C23); a new decision recorder appends it, a decisions sidecar replays it, and formation never hides it (C29). The three calculators are quick, declare `decisions` and run on change, so a pick or its void re-runs them on its frame; two analyses publish their topics.

**Tech Stack:** TypeScript (Node type stripping), pnpm monorepo, vitest + fast-check, node:sqlite, Svelte 5.

**Spec:** `docs/superpowers/specs/2026-11-06-sp4.1a-calibration-and-estimation-design.md` (approved by the user, 2026-11-06, with its review fixes and contract wording). The contract `docs/architecture.md`; answers A20–A30 in `docs/superpowers/specs/2026-11-05-sp4a/00-carry-over.md` §9; mockups `docs/design/2026-10-30-sp4a-displays/4-longrun.html`.

## Review Focus

1. **A session on a track with no calibration set and no track-file defaults** (`view.priors` and `view.track` both `notApplicable`): `degradation` starts from the config default with source `default`, `pit-loss` gives `unknown('insufficientData')` until a measured stop, never `NaN`. → Task 6 row 6, Task 7 row 7.
2. **A source whose stint is gone or whose session is stale** (deleted session, a rebuild that changed the stints, C61): the store marks it `missing` or `stale` on `calibration.values`, never throws, and the set's value rests on the rest. → Task 5 row 8.
3. **A flashback that voids a `calibrationChosen` decision**: `view.priors` returns to the session-start snapshot, and the topics equal a run that never received the pick (C27a, C33). → Task 3 row 9, Task 4 row 4.
4. **A pick on the grid or in the formation lap**: the decision stays in the projection and changes `view.priors` on its frame, while the formation lap's other facts stay hidden (C29). → Task 3 row 7, Task 4 row 5.
5. **A set edited after the pick**: the run and its replay keep the picked snapshot's values (C38, C62a). → Task 4 row 7.
6. **An override outside its declared range** (`calibration.override.set` with `deg 5000`): the bridge rejects it with a reason and stores nothing (C73). → Task 5 row 5.
7. **A stint of one lap or a stint with only in- and out-laps** as a source: its aggregate is `insufficientData`, the set ignores it for pooling, the panel shows why. → Task 6 row 8.
