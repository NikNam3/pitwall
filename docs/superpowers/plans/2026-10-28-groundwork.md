### Task 1: One file per topic in contracts

**Goal:** topic definitions live one per file in `packages/contracts/src/topics/`, and a generated index collects them, so adding a topic means adding a file (user decision Q-B; same pattern as ADR 0005 for features).

**Scope:** `packages/contracts`, `scripts`, `package.json` (root, scripts only), `.gitignore`, `apps/bridge`, `test`.

**Requirements:**
1. `packages/contracts/src/topic-def.ts`:
   - holds `TopicDef<P, V>` (as today: `name`, `mode: 'state' | 'append'`, `maxHz`, phantom `params?: P`, `value?: V`)
   - exports `defineTopic<P, V>(def: { mode; maxHz }): Omit<TopicDef<P, V>, 'name'>`
2. **One file per topic** in `packages/contracts/src/topics/`:
   - The file name is the topic name plus `.ts`: `feed.status.ts`, `session.info.ts`, `cars.overview.ts`, `car.detail.ts`, `car.telemetry.ts`, `laps.ts`, `stints.ts`, `pitStops.ts`, `flagPhases.ts`, `events.ts`, `insights.ts`.
   - Each file default-exports `defineTopic<P, V>({ mode, maxHz })` with today's mode, rate and types.
   - Each file also exports the DTO types that only that topic uses: `FeedStatus` in `feed.status.ts`, `SessionInfo` in `session.info.ts`, `CarOverview` in `cars.overview.ts`, `InsightEntry` in `insights.ts`.
   - Shared types stay in their own modules: `FeedInfo` and `ReservedCommand` move to `packages/contracts/src/feeds.ts` and `commands.ts`.
3. `scripts/gen-topics.ts`, modelled on `scripts/gen-features.ts`:
   - lists the `*.ts` files of `packages/contracts/src/topics/` (except `index.generated.ts`), sorted by code unit
   - **throws** for a file name that is not a valid topic name (`/^[a-z][A-Za-z0-9]*(\.[a-z][A-Za-z0-9]*)*$/`)
   - writes `packages/contracts/src/topics/index.generated.ts`:
     ```ts

     import topic0 from './car.detail.ts';
     …
     export const TOPICS = {
       'car.detail': { name: 'car.detail', ...topic0 },
       …
     } as const;
     ```
   - exports `findTopicFiles(dir)`, `renderTopicsIndex(names)` and `generateTopics(dir?, outFile?)`, like the features generator
4. `packages/contracts/src/topics.ts` re-exports `TOPICS` from the generated index and keeps `TopicName`, `TopicParams<T>` and `TopicValue<T>` with the same meaning. The public API of `@pitwall/contracts` stays source-compatible for importers (bridge code compiles unchanged except for moved type imports).
5. **Root scripts:**
   - add `gen:topics`
   - add `gen` (= `gen:features` and `gen:topics`)
   - every place that runs `gen:features` before tests, typecheck, acceptance or the bridge now runs `gen`
   - `.gitignore` lists `packages/contracts/src/topics/index.generated.ts`
6. `CONTRACT_VERSION` stays one constant in `version.ts`.

**Tests:**

### Task 4: The current version of each lap

**Goal:** one shared answer to "which record of car c, lap n is current?", usable by engine, strategy and UI (review F5).

**Requirements:**

### Task 5: Calculators run on demand

**Goal:** a calculator runs only when a subscribed topic needs it, or when it feeds no topic at all (for insights only). Spec 7.3, review F1.

**Scope:** `apps/bridge/src/hub`, `apps/bridge/src/pipeline`, `apps/bridge/src/features`, `apps/bridge/test`.

**Requirements:**
1. **`TopicHub`:**
   - add `subscribedTopics(feedId: FeedId): ReadonlySet<TopicName>`
   - add the option `onDemandChange?: (feedId: FeedId) => void`, called after `subscribe`, `unsubscribe` or `removeClient` changes the set of topics that have at least one subscription for a feed (only when the set actually changed)
   - with several listeners needed later, keep it a single callback; the bridge composes
2. **`FeedPipeline` / `SessionProcessor`:** the needed calculators are:
   - those bound (through `bindState`) to a topic in `hub.subscribedTopics(feedId)`
   - plus every calculator that no binding of any feature references
   - plus, transitively, what those read (the scheduler already resolves this)

   The pipeline calls `scheduler.setNeeded(...)` when a session's runner starts and again on every demand change while a session runs. Because the hub takes one callback, `serve` and `processRecording` wire `onDemandChange` to the pipeline. Keep the wiring local and simple.
3. **Behaviour:**
   - A newly needed calculator runs on the next frame where it is due and affected. The scheduler's pending-change bookkeeping already makes a late incremental calculator equal to one that ran all along.
   - No other change to the scheduler.
4. **Determinism tests and the acceptance hash** must subscribe to every topic before the replay starts, so they still cover every calculator. Adjust the test helpers; the hash must stay identical across two runs.

**Tests:**
- hub: the subscribed-set and callback semantics (two clients on one topic, unsubscribing one keeps the topic, `removeClient`, several feeds)
- pipeline: with no subscribers only the unbound calculators run; subscribing to `cars.overview` mid-session starts its calculator; unsubscribing stops it

### Task 6: Weekend context for every driver, automatic database rebuild

**Goal:**
- The weekend context carries every driver's laps from the player's earlier sessions, not only the player's own (review F7). The strategy needs rivals' practice pace and degradation, and the player's own feed sees every car.
- An outdated database rebuilds itself instead of failing.

**Scope:** `apps/bridge/src/storage`, `apps/bridge/src/pipeline`, `apps/bridge/src/cli`, `packages/engine/src/state` (granted: `weekend-context.ts`), `packages/engine/src` (only what the type change needs), `apps/bridge/test`, `packages/engine/test`.

**Requirements:**
1. **`WeekendContext`** (`packages/engine/src/state/weekend-context.ts`) becomes:
   ```ts
   type WeekendContext = {
     weekendId: string;
     driverKey: DriverKey;            // the player
     sessions: Array<{
       sessionUid: SessionUid;
       sessionType: number;
       drivers: Array<{ driverKey: DriverKey; laps: LapRecord[]; stints: StintRecord[]; pitStops: PitStopRecord[] }>;
     }>;
   };
   ```
   - `sessions` = the weekend's earlier sessions in which the player took part, oldest first (the same sessions as today).
   - `drivers` = every driver stored for that session, ordered by car id, each with their own records (the repository already filters by `DriverKey`).
2. **Schema mismatch:**
   - `openDatabase` with an old `user_version` no longer stops `live`. The `live` command deletes the database files and recreates them, logs `database schema <found> is outdated; rebuilding it from the recordings`, then runs the same rebuild `reprocess` does (all recordings) before serving.
   - `reprocess` itself is unchanged.
   - `SchemaVersionError` may remain for other callers.
3. Everything that reads `WeekendContext` (engine runner, tests) compiles against the new shape.
4. Out of scope (second car, later): storing two feeds of the same `sessionUid` side by side. Today's `session_uid` keys assume one feed per session; leave a doc comment on the `sessions` table DDL saying so.

**Tests:**
- `weekendContext` returns, per earlier session of the player, every stored driver with their records, ordered by car id
- a database with an old `user_version` makes `live` rebuild and then start (with a fake source)
- existing storage and weekend-context tests updated to the new shape

### Task 7: Jobs as part of features

**Goal:** an expensive computation (later Monte Carlo) can be declared in a feature, triggered by the scheduler, run in a worker, and published to a topic with what it was computed for (review F2).

**Scope:** `packages/engine/src/calc`, `packages/engine/test`, `apps/bridge/src/jobs`, `apps/bridge/src/features`, `apps/bridge/src/pipeline`, `apps/bridge/test`, `packages/contracts` (granted: one new file `src/computed.ts` plus its re-export).

**Requirements:**
1. **`Job<In, Out>` moves to `packages/engine/src/calc/types.ts`** (exported from the engine index):
   ```ts
   type Job<In, Out> = {
     kind: 'job';
     id: CalculatorId;
     reads: Dependency[];
     trigger: Cadence;
     prepare(view: EngineView): In;
     module: URL;
     readonly out?: Out;
   };
   ```
   `apps/bridge/src/jobs/job-runner.ts` imports it from there. `strategy` can now declare jobs.
2. **`packages/contracts/src/computed.ts`:** `type Computed<T> = { computedFor: { lap: number; frameId: number }; value: T }`. A job's topic value type is `Computed<…>`.
3. **`Feature`** gets `jobs?: Job<unknown, unknown>[]` and a binding helper `bindJob<T extends TopicName, Out>(topic: T, job: Job<unknown, Out>)`, allowed only when `Computed<Out>` is assignable to `TopicValue<T>`.
4. **Triggering through the scheduler:**
   - For every job, the pipeline registers a quick calculator `job:<id>` with the job's `reads` and `cadence: trigger`, whose `compute` is `prepare`.
   - When that calculator ran in a frame, the pipeline calls `JobRunner.trigger` with its output and `computedFor = { lap: <player's current lap>, frameId: frame.frameId }`.
   - Demand (Task 5) applies: the trigger calculator is needed only while its job's topic has a subscriber.
5. **Lifecycle and results:**
   - one `JobRunner` per `FeedPipeline`, seed `0`, closed when the pipeline stops
   - a result is published as a state value `{ computedFor, value }`
   - an error result marks the topic `errored` and logs the error
   - results that arrive after their session ended are dropped
6. Job topics are excluded from the determinism hash (results arrive asynchronously). Document that in the hash helper.

**Tests:**
- a fixture job module under `apps/bridge/test/` (e.g. returns `input + rng()`), declared in a test-only feature and bound to a test-only topic: subscribing triggers it on its cadence and the client gets `{ computedFor, value }`
- an error result marks the topic `errored`
- without a subscriber the job never runs
- a type-level test for `bindJob`

The test-only topic and feature must not leak into production: the generators only read their real folders, so construct the feature and topic in the test, e.g. by passing features to `FeedPipeline` directly and widening the topic type in the test only.

### Task 8: Read-only config for calculators (thresholds)

**Goal:** features declare configurable values (thresholds, windows, targets) with defaults. The engineer overrides them in a file. Calculators read them from `EngineView`, and each session stores the config it ran with, so replays reproduce alarms (review F6, user decision Q-C).

**Scope:** `packages/engine/src/calc`, `packages/engine/test`, `apps/bridge/src`, `apps/bridge/test`.

**Requirements:**
1. **Engine** (`packages/engine/src/calc/config.ts`, exported):
   - `type ConfigKey<C extends Record<string, number | string | boolean>> = { key: string; defaults: C; read(view: EngineView): C }`
   - `defineConfig(key, defaults)`; `read` returns `view.config[key]` merged over the defaults
   - `EngineView` gets `config: DeepReadonly<Record<string, Record<string, number | string | boolean>>>`
   - the scheduler passes it through (`SchedulerInput` carries it)
2. **Features:** `Feature` gets `config?: ConfigKey<…>[]`. Duplicate keys across features are a startup error.
3. **Bridge:**
   - `apps/bridge/src/feature-config.ts` loads `<PITWALL_DATA_DIR>/config.json` (missing file = defaults) of the shape `{ "<key>": { "<name>": value } }`
   - **Validation:** an unknown key or name, or a value whose `typeof` differs from the default's, is a `StartupError` naming the key and field
   - the effective config (defaults merged with overrides, only declared keys) is fixed for the bridge run
3a. **The config travels with each session:**
   - It is stored as `<session file>.config.json` next to each live session's `.pwrec.gz`, written when the session file opens.
   - `replay` and `reprocess` use `<recording>.config.json` next to the recording if it exists; otherwise the current effective config.
   - `processRecording` gets the config as a parameter.
4. No production feature declares config yet. A runtime change of config (UI) is out of scope; note it in the code where the config is fixed.

**Tests:**
- `defineConfig.read` with and without overrides
- loader validation cases (unknown key, unknown field, wrong type, missing file)
- a test-only feature whose quick calculator raises an insight above a configured threshold: with the default it does not fire; with an override in `config.json` it fires
- the sidecar is written for a live session (fake UDP source) and used by `replay`

### Task 10: Freshness data for the UI's stale check

**Goal:** the UI decides when a value is too old (user decision Q-D = B, review F9). It needs, per car, when each data source last updated it, and how often each source is expected. The rule then is one factor ("stale after about 3 missed updates"), not one threshold per number.

**Scope:** `packages/domain` (granted), `packages/contracts` (granted: `feed.status.ts`), `packages/engine/src/step`, `packages/engine/src/history`, `packages/engine/test`, `apps/bridge/src/features`, `apps/bridge/test`.

**Requirements:**
1. **`packages/domain/src/freshness.ts`** (exported from the domain index):
   - `type DataSource = 'lapData' | 'motion' | 'telemetry' | 'status' | 'motionEx' | 'damage' | 'tyreSets' | 'sessionHistory' | 'participants' | 'setups'`
   - `const SOURCE_INTERVAL_MS`: the expected interval per source from the F1 25 spec, or `'menuRate'` for the five menu-rate sources (`lapData`, `motion`, `telemetry`, `status`, `motionEx`). The rest: `damage: 100`, `setups: 500`, `participants: 5000`, `tyreSets: 1100`, `sessionHistory: 1100` (20/s rotating over up to 22 cars).
   - The doc comment says that menu-rate sources use the measured cadence (`feed.status.cadenceMs`) and that the UI applies its own factor.
2. **`CarState.updatedAt: Partial<Record<DataSource, SessionTime>>`:**
   - the session time of the last frame whose packet of that source carried data for this car (`MotionEx` and `setups` only for the player car; `tyreSets` and `sessionHistory` when the rotating packet named this car)
   - set by the sub-step that reads that source
   - starts empty (`{}`)
3. **`feed.status`** gets `cadenceMs?: number`, the median session-time step of closed frames. The assembler already measures it as `FrameMetrics.cadenceMs`.
4. **Remove `'stale'` from `UnknownReason`** in `packages/domain/src/known.ts`. Nothing produces it; the UI decides staleness.
5. **`car.detail`** carries `updatedAt` as part of `CarState`. `cars.overview` gets `updatedAt` too, so the timing tower can grey out a car whose timing stopped.

**Tests:**
- per source, a frame with that packet sets `updatedAt[source]` to the frame's session time for the cars it carries, and leaves other sources untouched
- a frame without the packet leaves it unchanged
- a flashback restores `updatedAt` with the snapshot (covered by the existing state round trip; add an assertion)
- `feed.status` carries `cadenceMs` after a few frames
- `UnknownReason` no longer accepts `'stale'` (type-level test)
