# SP4.3d2 The Planning Round: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In this repo every task has two phases by two agents (contract C82): a test agent writes the failing tests and commits them, an implementation agent makes them pass without touching tests or `gallery.ts`; the supervisor checks `git diff --stat <test-commit>..HEAD -- '*.test.ts' '**/test/**' test-support` is empty after every implement phase.

**Goal:** Between qualifying and the race the engineer prepares plans on the finished qualifying run: the session ends without waiting for the race's first packet, the feed is not stale in the gap, a planning job scores the DP's best per stop count, the prepared slots and the game's plans from the grid with the race's forecast, A and B are prefilled for a confirm, and the race commits the prepared plans at its first frame.

**Architecture:** Bottom-up (C81): contract text and types first; then the gap rules in the engine and bridge (session end by timer, between-sessions feed, the race's forecast kept, the ended qualifying run restored after a restart); then the analysis side (qualifying rows of the starting point's units, the grid start, the DP's free start compound, the planning job and prefill); then the bridge's planning module and the race-start commit; then the boards. One owner per judgement (C43): `forecast-field` builds every starting point (C50), `shared/grid.ts` owns the grid, the strategy unit owns the prefill, the bridge only stores, routes and publishes.

**Tech Stack:** TypeScript (Node type stripping), pnpm monorepo, vitest + fast-check, Svelte UI, Playwright, worker threads.

**Spec:** `docs/superpowers/specs/2026-11-16-sp4.3d-planning-design.md` (approved 2026-11-16, contract texts §9.2 included; this plan builds §7, §8's 4.3d2 lines, §9.2). Built on 4.3d1 (`docs/superpowers/plans/2026-11-16-sp4.3d1-race.md`, run log `docs/history/notes/2026-11-16-sp4.3d1-run-rulings.md` R1–R35): `activePlan` (R32), slots, `plan.*` routing, `bestPerStops`, the plan board with `source: live | planning`. Mockups (approved): `docs/design/2026-11-16-sp4.3d/plan-board.html` (planning round state), `plan-workbook.html` (planning round), README "What is drawn".

## Supervisor's calls in this plan (for the user's review of the plan)

1. **The planning base is the ended qualifying run's view**, not `asOfStored` over the stored projection: the race's sets left and forecast exist only in the live state (as-of R17, R19; spec §7.3 "replayed to its end"); the run's projection equals the stored one (C38). After a restart in the gap the feed replays the recording to get the same run back (Task 5). C62d's parenthesis gains "its live state at its end" (user, 2026-11-16: A), and, from the plan review, "with the race's laps as the user entered them in place of the session's" (the view's `fixed.totalLaps`, which the starting point's units read); added in Task 1 (user, 2026-11-16).
2. **Step 1 keeps the next session's forecast** (`nextForecast`: the samples of the session after this one in the weekend's structure), not every session's keyed by session type: a session-type key would put a signal into the live state (C13), and the planning round needs only the race after the last qualifying (spec §7.3 narrowed).
3. **The planning job mirrors the race's strategy job:** one per feed, one part per our car, each car with the teammate on its prepared active plan (spec §7.2 said "each for its own player car"); a team with one feed still gets both boards.
4. **The race's own grid uses the grid start** (Task 7): today the starting point is `notApplicable` until the leader's lap 2, so §7.1 step 7's grid prefill had no rows to come from.
5. **Accept is one uiAction** (`plans.prepare.accept`, `plan.accept`: save the slot and, without an active plan, activate it): a save and an activate in one frame reject the activate (4.3d1 R25).
6. **The boards switch by themselves:** `source` gains `auto` (the default): planning while the feed's round is open, live otherwise, by the board's presentation table (C66); the `plan` workbook serves both (spec §6.6).
7. **The qualifying rows** (spec §7.2) also apply when those units run live in a qualifying session (on demand, C49); live they see qualifying's own `totalLaps`, so their answer there is over that count, not the race's (only the planning view carries the entered laps, C62d). `race-interaction` needs one too (it is a starting-point unit the spec's list missed).
8. **Rivals' start compounds** are drawn from a measured config default (`rivalStartOdds`, from the AI's start compounds in the stored races) restricted to the compounds the car has a fresh set of, each with `rival-stops`' window for that compound.
9. **Each car's race pace before its first race lap comes from the weekend** (user, 2026-11-16: "add it as you recommend"): a new calculator `weekend-pace` (Task 6b) gives per car its practice long-run pace when it has enough laps, else its qualifying pace corrected to race trim, else unknown; both grid starts read it, and in the race a car without a green race lap of its own starts from it instead of degradation's stand-in car. Weekend data enters pace through `view.weekend` (C39, C62), beside the calibration set that still owns tyres, degradation and pit loss (4.1a); this reopens 4.1a's "weekend data only through calibration" for pace only.
10. **Every planning-round control is a command** (plan review, C72): `plans.prepare.laps`, `.save`, `.accept`, `.remove`, `.activate` and `plan.accept` are registered in `shell/commands/` with their arguments; the boards' buttons and the LAPS input invoke them by id through their panel. This ends R33/R34's "buttons send uiActions" exception for the new controls; 4.3d1's `plan.save`/`plan.commit` buttons stay as R33 left them (not this run's scope).

## Review Focus

1. **Long-format qualifying:** the end of Q1 or Q2 opens no planning round; Q3's grid holds every car: Q3's order, then Q2's eliminated by Q2 order, then Q1's; a car without a valid time at the back. → Task 7 rows 1–2, Task 10 row 3.
2. **A driver's car slot differs between qualifying and the race** (a lobby rejoin): the prepared plans follow the race number (C62); a race number not in the race is skipped, never committed to another car. → Task 11 rows 3–4.
3. **A sprint weekend's two rounds:** the shootout's round writes the `sprint` file, qualifying's the `grandPrix` file; the sprint commits only the sprint file, the grand prix only its own. → Task 10 row 2, Task 11 row 5.
4. **The race loads while a planning job runs** (or before the engineer is done): the job is cancelled, the round closes, the file as stored is committed; nothing of the in-flight preview. → Task 10 row 7, Task 11 row 1.
5. **A game plan whose start compound has no fresh set, or differs from the compound fitted on the race's grid:** its row is `infeasible: 'startCompound'`, still scored with the compound the car has. → Task 9 row 5.
