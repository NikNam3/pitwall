# UI shell (sub-project 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the UI every later display plugs into: a display contract, a UI kit, the data path, the shell in Electron windows, findability tooling and a save-and-see dev loop, proven end to end by one placeholder display.

**Architecture:**
- **Bridge (Node):** gains feed-independent `ui.*` topics, a `uiAction` and a `replayControl` message, realism mode in the engine, a replay transport, dev topics and `pitwall dev`.
- **`apps/ui` (Svelte 5, Vite):**
  - a typed topic store feeds widgets that declare their data statically (`declareWidget`)
  - the shell (windows, workbooks, docking, link groups, commands, top bar) renders them in panel frames
  - a kit (value cell, table, chart, canvas, size in character cells) keeps every widget consistent
- **`apps/desktop` (Electron):** a thin window manager around the same web app.

**Tech stack:**
- existing: TypeScript (strict, type stripping), pnpm workspaces, Vitest, fast-check, Stryker, dependency-cruiser, ESLint
- new: Svelte 5, Vite, svelte-check, eslint-plugin-svelte, dockview-core, uPlot, JetBrains Mono (variable font file, bundled), Electron, esbuild (desktop only), Playwright

**Spec:** `docs/superpowers/specs/2026-10-28-ui-shell-design.md`. The visual rules it builds on are in `docs/brainstorms/2026-10-28-ui-shell.md` sections 1 and 3.

## Review Focus

The five conditions most likely to hurt in real use that the spec doesn't spell out. Each one has a test in its owning task.
1. **The 14" monitor is unplugged** and a workbook window's saved geometry is off-screen. Electron should place it on the primary display, not invisibly. (Task 19)
2. **A new session starts while panels are open,** e.g. quali to race. Folded append state from the old session must be dropped, not merged into the new one. (Task 9)
3. **Two windows edit the same workbook at almost the same moment** (a panel drag in one, an option change in the other). Both changes should survive. (Task 2)
4. **The bridge restarts while windows are open.** After the reconnect, every panel shows the bridge's state again, with no duplicate subscriptions and no lost link-group choices. (Task 9, Task 15)
5. **"Jump to lap N" beyond the recording's end, or the player's car changing between sessions.** The replay should stop at the last frame with a note, and "player" in a link group should resolve to the new car id. (Task 5, Task 16)

### Task 2: UI state in the bridge

**Goal:** workbooks, link groups, alert state, settings and key bindings live in the bridge, are saved in `PITWALL_DATA_DIR/ui/`, are shared by every window, and change only through `uiAction` (spec 7.2, 7.5, 7.7, 7.8).

**Scope:** `packages/contracts` (granted: `src/ui/`, `src/topics/ui.*.ts`, `messages.ts`, `wire.ts`, `index.ts`), `apps/bridge/src/ui-state` (new), `apps/bridge/src/ws`, `apps/bridge/src/cli/serve.ts`, `apps/bridge/src/storage/data-dir.ts`, `apps/bridge/test`, `packages/contracts/test`, `docs/decisions`.

**Depends on:** Task 1.

**Interfaces:**
- Produces, in `packages/contracts/src/ui/`:
  ```ts
  type WindowId = string;
  type Geometry = { screen: number; x: number; y: number; width: number; height: number };
  type PanelSpec = { widget: string; options: Record<string, unknown>; linkGroup: number };
  type WorkbookWindow = { id: WindowId; geometry?: Geometry; fontPx?: number; layout: unknown; panels: Record<string, PanelSpec> };
  type Workbook = { name: string; windows: WorkbookWindow[] };
  type CarRef = 'player' | 'teammate' | CarId;
  type TimeWindow = { kind: 'live' } | { kind: 'lap'; lap: number } | { kind: 'range'; from: number; to: number };
  type LinkGroup = { id: number; feedId?: FeedId; primary: CarRef; compare: CarRef[]; window: TimeWindow };
  type UiAction =
    | { kind: 'workbook.open'; name: string }
    | { kind: 'workbook.saveAs'; name: string }
    | { kind: 'workbook.updateWindow'; window: WorkbookWindow }
    | { kind: 'linkGroup.set'; group: LinkGroup }
    | { kind: 'alert.ack'; key: string }
    | { kind: 'alert.ackAll'; keys: string[] }
    | { kind: 'alertGroup.mute'; category: InsightCategory; muted: boolean }
    | { kind: 'realism.set'; enabled: boolean };
  ```
- Global topics with owner `core`:
  - `ui.workbooks`: `{ names: string[]; active: Workbook; error?: string }`
  - `ui.linkGroups`: `LinkGroup[]`
  - `ui.alerts`: `{ acknowledged: string[]; muted: InsightCategory[] }`
  - `ui.settings`: `{ realismNextSession: boolean; keys: Record<string, unknown> }`
- Messages:
  - `ClientMessage` adds `{ type: 'uiAction'; id: string; action: UiAction }`
  - `ServerMessage` adds `{ type: 'actionResult'; id: string; ok: true } | { type: 'actionResult'; id: string; ok: false; reason: 'invalid' | 'notSupported' }`
- `class UiState` in `apps/bridge/src/ui-state/ui-state.ts`:
  - `static open(dir: string, hub: TopicHub, log: Logger): UiState`
  - `apply(action: UiAction): { ok: true } | { ok: false; reason: 'invalid' }`
  - `realismNextSession(): boolean` (Task 4 reads it)
  - `close(): void`
- `DataDir` gains `ui: string` (`<root>/ui`).

**Requirements:**
1. **Files:**
   - `ui/workbooks/<name>.json`
   - `ui/state.json` (`{ activeWorkbook, linkGroups, acknowledged, muted, realism }`)
   - `ui/keys.json`, which is optional and only read
   - **The first start** creates `ui/workbooks/default.json`: one window `main` with one panel `{ widget: 'feed-status', options: {}, linkGroup: 1 }` and an empty layout. It also sets link group 1 to `{ id: 1, primary: 'player', compare: [], window: { kind: 'live' } }`.
2. **Validation is structural only**, because the bridge doesn't know widgets:
   - the shapes above; a panel's `options` must be an object
   - `layout` is kept as is
   - widget names and option values are the UI's job (Task 15)
   - `decodeClientMessage` rebuilds `uiAction` from known fields only and never throws, like the other decoders
   - `wire.ts` decodes `actionResult`
3. **`workbook.updateWindow` replaces one window by id** (or adds it) in the active workbook. Changes to two different windows never overwrite each other (Review Focus 3).
4. **Autosave and hand edits** (spec 7.2):
   - Writes are debounced by 300 ms. Each write is atomic: write a temp file, then rename.
   - The bridge keeps the SHA-256 of what it last wrote or read per file.
   - `fs.watch` on `ui/workbooks/` re-reads a file whose content hash differs. If it's the active workbook, the bridge publishes it.
   - If the active file is invalid JSON or the wrong shape, `ui.workbooks.error` holds the parse message, `active` stays at the last good version, and autosave of that file pauses until a valid version is read.
5. **`ui.settings.keys`** is `keys.json` parsed as an object, `{}` if missing. Invalid JSON gives `{}` and logs a warning. The UI does the lenient parsing (Task 16). The file is watched like the workbooks.
6. **`alert.ackAll`** takes the keys the UI saw, so an alert raised in between isn't acknowledged unseen.
7. **`realism.set`** only changes `state.json` and `ui.settings.realismNextSession`. It never changes the running session (spec 7.9; Task 4 applies it).
8. **ADR 0013, "UI state owned by the bridge":** files, atomic writes, the hand-edit rule, why the bridge and not `localStorage`.

**Tests:** in `apps/bridge/test/ui-state/`, all with a temp data dir:
- a fresh directory gets `default.json` and the link group default
- two `updateWindow` actions for windows `a` and `b` within 10 ms both end up in the file after the debounce
- a hand edit (write a new file with a different hash) publishes the new `active`
- the bridge's own write doesn't trigger a re-publish
- an invalid-JSON hand edit sets `error`, keeps `active`, and a following `updateWindow` doesn't overwrite the file; writing valid JSON clears `error`
- `alert.ackAll` with `['a']` while `b` is active acknowledges only `a`
- `realism.set` changes `ui.settings` and `state.json`
- wire tests: every `UiAction` kind round-trips; an unknown kind, a missing field or a non-object `options` decodes to `undefined`
- ws test: a `uiAction` gets `actionResult ok: true` and the subscribers of `ui.linkGroups` get an update

### Task 5: Replay transport

**Goal:** a replay feed can be paused, sped up and jumped to a lap, from a client message (spec 8.5).

**Scope:** `packages/contracts` (granted: `messages.ts`, `wire.ts`, `src/topics/replay.status.ts`), `apps/bridge/src/input`, `apps/bridge/src/replay` (new), `apps/bridge/src/pipeline`, `apps/bridge/src/ws`, `apps/bridge/src/cli`, `apps/bridge/test`, `packages/contracts/test`.

**Depends on:** Task 1.

**Interfaces:**
- Produces:
  - `type ReplayControl = { kind: 'pause' } | { kind: 'play' } | { kind: 'speed'; factor: number } | { kind: 'jumpToLap'; lap: number } | { kind: 'jumpToTime'; sessionTimeMs: number }`
  - `ClientMessage` adds `{ type: 'replayControl'; id: string; control: ReplayControl }`; the answer is `actionResult` (Task 2's type; `notSupported` for a live feed)
  - topic `replay.status` (owner `core`, scope feed, state, 4 Hz): `{ paused: boolean; speed: number; sessionTimeMs: number; playerLap: number; atEnd: boolean; note?: 'beyondEnd' }`
  - `class ReplayController` in `apps/bridge/src/replay/replay-controller.ts`:
    - `constructor(opts: { path: string; feedId: FeedId; makePipeline: (source: PacketSource) => FeedPipeline; hub: TopicHub })`
    - `control(c: ReplayControl): void`
    - `position(): { sessionTimeMs: number; playerLap: number } | undefined`
    - `done: Promise<void>`
  - `FeedPipeline.position()`, which `ReplayController` uses
  - CLI: `pitwall replay <file> [--paused] [--speed <n>] [--at-lap <n> | --at-time <ms>]`

**Requirements:**
1. **`PwrecSource` gets a `pacer`:** `{ wait(recordGapMs: number, signal): Promise<void> }`, owned by the controller. The pacer:
   - waits `gap / speed` while playing
   - blocks while paused
   - doesn't wait while fast-forwarding
   - The existing `mode` option maps onto a fixed pacer.
2. **Forward jump:** fast-forward until `position()` reaches the target, then restore the previous paused or playing state.
3. **Backward jump:** stop the pipeline, `hub.resetFeed(feedId)`, start a new `PwrecSource` from the file start, and fast-forward to the target.
4. **A jump beyond the end** stops at the last frame with `atEnd: true, note: 'beyondEnd'` and doesn't hang (Review Focus 5).
5. `--at-lap` and `--at-time` jump before `listening` is printed. `--paused` starts paused.

**Tests:** on the committed `tt-zandvoort-lap1` segment and the fixture recording via `describeWithFixture('ttZandvoort', …)`:
- pause stops `sessionTimeMs` from advancing
- speed 4 advances about 4× faster on an injected clock
- `jumpToLap 5`, then `jumpToLap 2`, gives the same `session.info` and `cars.overview` values as a fresh replay fast-forwarded to lap 2
- `jumpToLap 99` ends with `note: 'beyondEnd'` within the test timeout
- `replayControl` on a live (`ManualSource`) feed gets `notSupported`
- wire round-trip for every control kind
