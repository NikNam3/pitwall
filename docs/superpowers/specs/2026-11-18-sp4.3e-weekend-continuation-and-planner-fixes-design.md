# SP4.3e: weekend continuation and planner fixes (design)

Status: draft for the user's approval, 2026-11-18. Input: the Texas live test of 2026-11-17 (`docs/acceptance/live-checklist.md`, 2026-11-17 sections) and the research report `~/dev/personal/pitwall-research/live-test-2026-11-17/planner-report.md` (root causes verified in code, storage and recording bytes).

## 1. Intent

The league ran a full Texas weekend on 2026-11-17 (1 h practice, short qualifying), then the EA servers crashed before the race. The race (56 laps, grand prix) is driven on 2026-11-18 in a **new lobby**, with **no qualifying** (the grid is set by hand to tonight's qualifying order) and at most a short practice. The drivers practised a lot already; they must not have to do another full practice.

So pitwall must:

1. carry the 2026-11-17 weekend forward into the 2026-11-18 race: the weekend's practice and qualifying (pace per car, the grid, the planning round) as if it were the same weekend; driver profiles and the calibration set already carry over (they are per person and per track);
2. produce good plans: the planning round on 2026-11-17's qualifying gave wrong grids, `insufficientData`, an inter plan in the dry and a missed better plan. Its root causes are fixed properly, not patched;
3. be verified before the race: the data and the plans are checked against what we know is true (§6).

In general a full practice before a race stays the normal case; continuation is for a weekend interrupted between its sessions (a crash, a split evening).

## 2. Goals, non-goals, anti-goals

**Goals**
- G1. The user declares, before a session starts, that a feed's next session continues weekend W. That session then sees W's earlier sessions as its weekend context (`view.weekend`, C39, C62), W's planning round and W's prepared plans (C62d), exactly as if it had W's weekend id.
- G2. The planning round can be reopened on W's stored, ended qualifying at any time between that qualifying and the continuing race (not only right after it ends or at a bridge start whose newest session is that qualifying).
- G3. The planner's root causes 1–5 and 6g of the report are fixed (§4).
- G4. A readiness check (§6) shows, before the race, that the grid, every car's pace, the sets, the candidates and the calibration values are plausible.
- G5. Tonight's temporary changes are reverted (§7).

**Non-goals**
- Automatic continuation (approach B, §3): rejected.
- Carrying weekends across tracks, or more than one continued weekend at once.
- Pace per car as a track prior in the calibration set (approach C): later, if at all.
- The degradation priors' full remodel (report §5, fixes 2–4: race-length compatibility, uncertainty flag, first-lap effect): a later spec with validation on races (memory: SP4.3 enhanced care). Only fix 1 (paired offsets) is in scope, see §4.6.
- UI items 6c (link-group pin), 6d (person names), 6e (calibration edit off the main thread), 6f (manual stint exclusion): next sub-project, listed in §8.

**Anti-goals** (a failure even if it works)
- A continuation that happens without the user's declaration, or that a replay or reprocess does not reproduce (C38).
- Any fix that patches a reader instead of the owner of a judgement (C43; memory: structural fixes, not workarounds).
- A grid, pace or plan that silently uses a 0 or a made-up value (C3): every stand-in is declared and marked.

## 3. Approaches (the user picked A)

- **A. Declared continuation (picked).** A command in the shell (and a CLI call) "the next session continues weekend W". The bridge writes the declaration to a sidecar of that session's recording; the session's weekend id for the weekend context, the planning round and the prepared plans is W. Explicit, deterministic, no surprise; one action before the race; a contract change (C62, C62d).
- **B. Automatic continuation** (same track, same team and race numbers, within N hours). No action, but it fires when unwanted (a new weekend at the same track), is hard to see, and needs the same contract change. Rejected.
- **C. Pace as a track prior** in the calibration set. Outlives the weekend but covers neither the grid nor the planning round; AI pace depends on AI difficulty; larger. Rejected for now.

## 4. Design

### 4.1 The contract change (C0: first, with the ADR line, before any code)

Proposed wording (to be approved with this design; ADR 0015 gets the reasons):

- **C62 (addition):** "A weekend may continue an earlier weekend of the same track: before its first session starts, the user declares by a uiAction that the team's next weekend continues weekend W. Every session of that weekend (the declaration holds until the weekend ends or the user clears it) then has as its weekend context W's sessions and its own weekend's earlier sessions, loaded as this clause loads them (the player's, by team and race number), and the weekend id the planning round, the prepared plans and the plan decisions use is W. The declaration applies to all the team's feeds (C1a). The bridge writes it to each session's weekend sidecar; it is fixed for the session; a replay reads the sidecar; a recording without one continues nothing. A declaration for a track other than the session's is void and the session continues nothing."
- **C62d (addition):** "On a uiAction the bridge opens the planning round of weekend W on W's newest stored ended qualifying, whenever no session runs on the feed; it is the same round as at that qualifying's end. A race that continues W (C62) commits W's prepared plans at its first frame as a race of W does."
- **C75 (addition to the list of what takes effect when):** "a weekend-continuation declaration takes effect at the next session start (C62)."
- Glossary: "continued weekend: the weekend a session continues by the user's declaration (C62)."

No other clause changes. The declaration is not a decision fact (it is fixed before the session, like the profiles snapshot), so C76 is untouched.

### 4.2 Continuation in the bridge

- A uiAction `weekend.continue { team, weekendId | null }` (per team: all the team's feeds, C1a; my call, so both feeds always agree) and a shell command "Weekend: continue <weekend>" (C72), plus `pitwall weekend continue <weekendId>` and `pitwall weekend` (lists stored weekends per track with their sessions, and the pending declaration per feed). The command offers the stored weekends of the track the feed last saw, newest first.
- The declaration is UI state of the bridge (C70: `ui.*` topic `ui.continuation`). It binds to the first new weekend id a session of the team brings after the declaration (my call: the whole new lobby weekend continues W, so a short practice before the race also counts, and the race sees it), holds for every session of that weekend, and is cleared by `null` or when a session of a third weekend starts. At each session start the pipeline checks the track: a match writes the sidecar `<recording>.weekend.json` `{ continues: W }` and uses W; a mismatch logs a warning, writes `{ continues: null, declared: W, reason: 'otherTrack' }` and continues nothing.
- `SessionStorage.weekendContext` (the one loader, C62) loads, when the sidecar says W, W's sessions followed by the session's own weekend's earlier sessions (oldest first), else the session's own weekend's. Tonight's alias hack (`PITWALL_WEEKEND_ALIAS`) is deleted.
- Storage keys stay the game's (session uid, weekend id, player car, C60): the continuing race is stored under its own weekend id. The weekend sidecar is what links it, and the stored session row records the effective weekend in its settings JSON so `pitwall weekend` can show it (no schema change).
- Replay and reprocess read the sidecar (C38, C59). Tests: determinism with and without the sidecar.

### 4.3 The planning round on a stored qualifying

- A uiAction `plans.round.open { feedId, weekendId }` (and a command "Planning: open round for <weekend>"): when no session runs on the feed, the bridge replays W's newest stored ended qualifying of that feed's player seat as the startup restore does (C59, C61: the same restore path, `restoreEndedSessions`), opens its round and publishes `plans.prepared` / `plans.preview` as today.
- The startup restore is unchanged (its newest-session rule), so a bridge restart after the fun GP of 2026-11-17 does not reopen the round by itself; the command does. (Checked: the aborted race and the fun GP of 2026-11-17 ran under their own weekend ids 3025857561 and 2005203671, so W = 548397152 holds only the practice and the qualifying.)
- The race-start commit (C62d, `planning/race-start.ts`) looks the prepared plans up under the race's effective weekend id (§4.2).

### 4.4 Planner fixes (no contract change; report §1–§4, 6g)

Each item: owner module, what changes, the report's tests. Every recorder or sub-machine change changes the rules version (C61, C90): stored sessions rebuild.

1. **Laps recorder: a lap completes only at a crossing of the line** (report §1; `engine/src/recorders/laps.ts`, `lap-boundary.ts`). A rise of the lap number without a crossing (lap distance falls by more than half the track length, or from below 0 to 0 or more) appends no lap and marks the lap number not completed, so Session History confirms nothing for it either. Segment tests on both qualifying recordings around 1115–1121 s.
2. **`car-activity-timed`: the in-lap status at the line is a pending confirmation** (report §2; `situations/car-activity-timed/timed.ts`, C18). Declared transitions unchanged; the transition table rows split (status mid-lap / on the tick before the line); segment tests DR 214–219 s (car 18), ASY 443–448 s (car 9); `pitwall scan-situations` over every recording in the report (C85).
3. **Race sets in the race's starting point** (report F3a; `analysis/src/shared/forecast-field`, the one builder, C50): on a grid start the sets are those `available` now plus those with `recommendedSession` equal to the race's session type. **For a continued weekend whose race runs in a new lobby (user, 2026-11-18: the lobby gives every driver a fresh full allocation),** the planning round plans with a fresh race allocation instead of the qualifying's sets: per car the dry compounds' counts of a race-only weekend's allocation (a config entry of the builder, `freshRaceSets`, C47, its defaults measured from a race-only lobby's first TyreSets; until measured, the 2026-11-04 race's first TyreSets as the source). Which allocation applies is part of the continuation: a race of a continued weekend that starts in a new lobby reads `freshRaceSets`. The live strategy reads the race's real sets from its first TyreSets as today; the readiness check (§6) compares the plans' sets with the real ones at tomorrow's race load. The fitted-set question (does a used qualifying set count as a start option) is settled by the builder as: the race's free start may use any set the race has (used ones included) and the DP's free start keeps taking a new set unless only used ones exist; marked as the builder's call in the plan.
4. **The rain filter is never bypassed; one owner** (report F3b, F3c): `bestPlanOf` and `candidatesOf` apply `allowed` to every fallback; with nothing allowed the car's entry is infeasible (C3). `rainCanCome`/`allowedOf` move to one shared pure function (or calculator) read by `strategy`, `pit-window` and the Box call (C43).
5. **One set-feasibility rule and the planning cap** (report F4b, F4c): one shared pure function "the sets a policy uses from a starting point" for the DP and `followable`; `partFinalCall` takes the cap from the chosen MC config (6,000 in the planning round, R34).
6. **Degradation α offsets as paired differences** (report §5 fix 1; `degradation/priors.ts`, its entry `version` changes, the priors store recomputes, C62a): per (session, car) the compound's α minus that car's medium α in the same session, then pooled; sources without a pair give ν but no offset. As a data step (no code): remove the 2026-11-04 race stints from `tx-1104` (its tyre life is half the race's, report §5c).
7. **A declared pace stand-in** (report 6g; in `weekend-pace`, the owner of pre-race pace, C43): a car with no long run and no valid qualifying lap takes the field's median qualifying pace plus a config offset (`noPaceStandInOffsetMs`, `config.ts`, C47), marked `standIn: true` in the output; the grid start reads it like any pace. Tonight's TEMP HACK in `forecast-field` is deleted.
8. **The planning-round save on the teammate's board** (report 6a): the two silent-ok `invoke` defaults (`kit/commands.ts`, `Panel.svelte`) answer `notSupported`; the teammate board's panel gets the registry's `invoke`. (C72, C73.)

`minLongRunLaps` stays 8 (the config default); the stand-in (7) and the in-lap fix (2) make the lower value unnecessary. To be checked in §6.

### 4.5 Order and tasks

Contracts first (C81): the contract and ADR change (§4.1); then the domain and contracts types (supervisor: the weekend sidecar type, the uiActions, `ui.continuation`, the `standIn` flag); then, two phases each (C82), with up to 8 parallel workers (memory: agent limit 8):

- T1 laps recorder (4.4.1) · T2 car-activity-timed (4.4.2) · T3 race sets + set rule (4.4.3, 4.4.5) · T4 rain filter owner (4.4.4) · T5 degradation paired offsets (4.4.6) · T6 pace stand-in (4.4.7) · T7 continuation in the bridge (4.2, 4.3) · T8 board save (4.4.8).

T1 and T2 share the rules-version rebuild; T3 and T5 both touch the planning round's inputs but different modules. Then `pnpm check`, a rebuild of stored sessions (once, at the end), `scan-situations` (T2), and §6.

## 5. Constraints

- The contract binds every change (C0); the contract change in §4.1 needs the user's approval with this design.
- Deadline: before the 2026-11-18 race, in the evening (user, 2026-11-18); the bridge may be stopped, rebuilt and restarted any time during the day. If time runs short, the order of value is: T7 (without it nothing carries over), T1, T2, T3, T6, T4, T5, T8. Anything not done falls back to: the race without a planning round, the live strategy from lap 2–3.
- Compute: one reprocess at a time, `vitest --maxWorkers=3`, keep ≥ 6 GB free (memory). The rebuild of 236 stored sessions after T1/T2 takes long: run it once, at the end, with the machine otherwise idle.
- Tests on real data as segments only (C84); no test reads storage or the data dir.

## 6. Readiness check (before the race)

A script in the research repo (`live-test-2026-11-17/readiness.mjs`, read-only on storage and the bridge's topics) and a short checklist entry. After the rebuild, with the bridge running and the round reopened on 2026-11-17's qualifying (`plans.round.open`):

1. **Grid:** both feeds give the same grid, equal to the full-lap order (DR P1 1:35.365, Verstappen P2, … ASY P14 1:37.643, Hadjar P20).
2. **Pace:** every grid car has a `weekend-pace` value or a marked stand-in; no `insufficientData`.
3. **In-laps:** no AI flying lap of the qualifying is an in-lap on either feed.
4. **Sets:** the planning round plans with the fresh race allocation (`freshRaceSets`); at the race's load, the real TyreSets of both our cars match it (else the plans are re-checked before lights out).
5. **Candidates:** both our cars get several candidates per stop count, none with inters (rain 1 %); DR's DP list contains a medium-medium-soft 2-stop.
6. **Calibration:** `tx-1104` without the 11-04 race and with paired offsets: the hard offset clearly slower than medium (DR's sources alone gave hard +1570 ms and soft +167 ms against medium, report §5a; the paired rule should land near those); the values shown to the user before the race.
7. **Continuation dry run:** a replay of a short recording with a weekend sidecar shows `view.weekend` = W's sessions and the commit under W.

A failing point is reported to the user with its effect on the race before the race starts.
