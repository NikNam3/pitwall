## 1. The track sidecar is always written

**Problem.** A session on a track without a valid track file writes no track sidecar (`feed-pipeline.ts`, `#openSessionFile`). Its replay then loads the committed file, so committing a file for that track later changes the replay's stream (C38).

### 1.1 Contract change (C0, first task)

Approved by the user, 2026-11-06 (option A). Lands before any code of this run.

**C62b**, the sentence "it is fixed for the run and written as a sidecar next to the recording; a replay uses the sidecar, and a recording without one loads the committed file as a live session does." becomes:

> it is fixed for the run and written as a sidecar next to the recording, also when the session has no valid file (the sidecar then records `notApplicable`); a replay uses the sidecar, and a recording without any sidecar loads the committed file as a live session does.

**ADR 0015**, the C62b line gains at its end:

> A session without a valid file writes a not-applicable sidecar, so committing a file for its track later does not change its replay (user, 2026-11-06).

C38 and C59 keep their text: both already name the track file among the sidecars.

### 1.2 Bridge

- `#openSessionFile` writes `<recording>.track.json` for every session: a known track as the `TrackFile` JSON (as today, so the 4.0 recordings stay valid), an unknown one as `{ "known": false, "reason": "notApplicable" }`.
- `readTrackFile` (`apps/bridge/src/track-files/load.ts`) recognises exactly that shape and returns `unknown('notApplicable')` without a warning. Any other content is validated as a `TrackFile`, as today (a failing one is `notApplicable` with one warning, never the committed file).
- `recordingTrack` is unchanged in shape: the sidecar if present, else the committed file. The `import` command already copies whatever sidecar exists.

### 1.3 Tests (`apps/bridge/test/`)

- A live session on a track id without a committed file writes the not-applicable sidecar; one on a track with a file writes the file (exists, keep).
- A replay of a recording with a not-applicable sidecar gives `view.track` `notApplicable` even when the tracks directory holds a valid file for its track id (a temporary tracks dir, C84).
- A recording without any sidecar still loads the committed file (exists, keep).
- A not-applicable sidecar logs no warning; a corrupt sidecar still logs one.

## 2. Panel edit mode

**Problem.** Adding a panel works only through the palette (`panel.add.<widget>`, Ctrl+K), and nothing removes one (user, 2026-11-06). The user chose an edit-mode toggle: the controls appear only while it is on, so during a race the panels look as now.

### 2.1 Behaviour

- **Toggle.** A top-bar toggle (kit text `edit layout`) and the command `layout.edit.toggle`, default key `Ctrl+E` (`DEFAULT_KEYS`; `keys.json` overrides it). Edit mode is window-local (C73): each window has its own, off at start and after a reload. The toggle shows its state (on: `text` bold; off: `textFaint`), theme roles only (C68).
- **Add.** While on, each dock group's tab strip ends with a `+`. A click makes that group active and opens the palette filtered to the `panel.add.<widget>` commands; picking one adds the panel to that group (the existing command, which adds to the active group).
- **Remove.** While on, each panel header shows a `×` after the gear. A click invokes `panel.remove.<panelId>`: one command per panel of the window (as `window.focus.<id>` per window), titled `Remove panel: <panel title>`, also listed in the palette while edit mode is on. Removing the last panel of a group removes the group (dockview's default); removing every panel leaves the window empty, which shows the empty-window picker as today.
- **Saving.** A removal (or an addition) changes the dock layout; the window saves it through the existing `workbook.updateWindow` uiAction, as a drag does today. No new uiAction. The change takes effect when the bridge publishes it (C73).
- **Off.** Headers and tab strips render exactly as today; the `panel.remove.*` commands are not in the registry.
- Adding or removing a panel switches no workbook or layout: the layout controller is untouched (C67).

### 2.2 Ownership

`apps/ui/src/shell/**` and `apps/ui/src/kit/text.ts` are supervisor-owned (C78). The supervisor delegates this one change ("panel edit mode, spec section 2") to one test agent and one implement agent, scope `apps/ui/src/shell` and `apps/ui/src/kit/text.ts` (C82).

### 2.3 Tests (`apps/ui/test/`)

- Registry: `layout.edit.toggle` exists with default key `Ctrl+E`; `panel.remove.<id>` exists for each panel of the window only while edit mode is on.
- The `+` and `×` controls are absent with edit mode off and present with it on (component tests).
- `panel.remove.<id>` sends `workbook.updateWindow` with the window's layout without that panel.
- The `+` of a group that is not active adds the picked panel to that group.
- Edit mode is off after the window shell is rebuilt (reload).
- No new screenshot baseline: the edit-mode controls are covered by component tests; the screenshot budget stays at 52.

## 3. `pnpm desktop` builds after `gen`

**Problem.** `apps/desktop`'s `start` builds the UI before anything regenerates the widget index, so the first start after a new widget shows the old widget list.

**Change.** `apps/desktop/package.json` `start` becomes `pnpm -w gen && pnpm --filter @pitwall/ui build && pnpm build && electron .`. A supervisor commit (`build:`), no test: `package.json` is supervisor-owned (C78) and a start script has no unit to test.
