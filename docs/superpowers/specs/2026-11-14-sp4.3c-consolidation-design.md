# SP4.3c: one owner per judgement (consolidation, strategy fixes, live-test fixes)

Status: brainstormed with the user 2026-11-14; awaiting the user's approval. Inputs: `2026-11-14-consolidation-map.md` (the survey result, with every file:line; reports in `~/dev/personal/pitwall-research/consolidation-survey/01–06`), `2026-11-14-strategy-fixes-DRAFT.md` (superseded by this spec), `docs/superpowers/plans/2026-11-14-live-test-triage-questions.md` (T-numbers), research 20, 21 and 22.

## 1. Intent

The user: "the important thing is that the code stays clean. Be careful to not workaround to fix the strategy but improve it structurally"; "the cleaner the code the better (as long as it still stays correct); consolidating models makes future iterative improvements a lot easier."

Six read-only surveys found the same pattern across the analysis package: one judgement computed in several places (two dry references, five definitions of a car's pace, wear defaults in four configs, three rejoin models, four rival policies, ten medians), and nine places where today's code breaks the contract or a spec. The Silverstone live test of 2026-11-14 showed the cost: the strategy table never offered the right call (stay out on inters) because its parts judged the tyres, the weather and the candidates differently.

So this sub-project gives every judgement exactly one owner (C43), moves every reader onto it, deletes every other copy, and fixes the strategy and live-test findings as part of that, not beside it.

## 2. Goals, non-goals, anti-goals

**Goals**
- One owner per judgement, as in §5; every other copy deleted in the same task that moves its readers.
- A tyre model that is modular by tyre type, so each type's model can be improved alone (user).
- The 70 % wear limit as a hard rule in every unit that plans or shows a stop (user: "over 70 % we risk a puncture").
- The strategy fixes (T1–T8, T10, T11, T19, T21) and the live-test fixes (gap chart, ghosts and driver codes, restart, tyre bands, default workbooks that reach the user, §5.9). T10/T11 are the track-data generator's dry-year fallback for pit loss and compound offsets (`~/dev/personal/pitwall-trackdata`, its own commit) and the regenerated `data/tracks/**` (supervisor, C78, C62b); the Silverstone validation runs on them (supervisor's call: without them it measures the pit-loss fallback, not the model).
- A guard against a second owner returning.

**Non-goals**
- The planning displays (V17 plan board, V06 strategy overview, V01 circle of doom): they become SP4.3d, built on the consolidated model (the supervisor's call: they should show plans from one model).
- The medium-confidence model terms of research 21 §10: wetness slopes, cold-tyre laps 2–3, the 1.075 crossover line, settled wetness by rain %. Each can later be one tyre type's or `track-wetness`'s change after a forecast-score sweep (ETH HPC).
- Pit loss by track pace (deferred item 10).

**Anti-goals** (a failure even if it works)
- A second owner of any judgement in §5, even temporarily on the integration branch (approach A, §4).
- A special case, reserved slot or copied value to make one race come out right (the user rejected a reserved inter slot as "a hack").
- A number changed that is not a bug fix or a deliberate model change of steps 3–5 (§8).

## 3. Constraints

- **The contract binds every change.** One clause changed, approved by the user and already committed (3568482e): C59 "A session's recording continues across bridge restarts: a restarted run replays it and appends to it." No other contract change is needed; a task that finds one stops and reports a contract gap (C0).
- **Supervisor-owned (C78):** `packages/domain/**`, contracts except a unit's own topic files, the engine core and recorders' registry, the UI kit, shell, theme and emphasis, configs at root, generated indexes. These changes are made or delegated by the supervisor before the test agents of their step start (C81).
- **Rules version (C61):** step 3's new recorder changes it; every stored session is rebuilt once from its recording at the next bridge start.
- **Two phases per task (C82)**, tests first; worker launch as `docs/superpowers` runs before (worktree per task, `PITWALL_PHASE`, `PITWALL_WORKER_SCOPE`).
- **Compute:** one reprocess, score or capture at a time; vitest `--maxWorkers=3`; keep ≥ 6 GB free (user, 2026-11-13).
- **Budgets:** existing speed budgets stay (`*.budget.test.ts`); new ones are stated in §7. A measurement over budget lowers a cap, never raises a budget.
- **Screenshots:** the fixed `SCREENSHOT_BUDGET` is not raised; baselines touched are re-baselined, not added.

## 4. Approaches

- **A. Move and delete in the same task (chosen by the user).** Each task builds or extends its owner, moves every reader onto it and deletes the old copies before it merges to the integration branch `sp4.3c/integ`. Each of the six steps ends with `pnpm check` on the branch; main receives the sub-project at the end. Cost: bigger tasks; tasks that run in parallel are split so they never share a reader.
- B. Build beside, switch later: new owners first, readers in a second pass, deletions last. Rejected: weeks with two owners and a clean-up that slips, against the point of the sub-project.
- C. One step per merge to main: rejected, main would carry a half-old, half-new strategy between steps 3 and 5.

### 5.2 The tyre model (O1, O1a)

**`tyre-model`, a new calculator** with an as-of form (for `forecast-score`'s past builds, as `forecast-field` has). `degradation` stays the pace fitter; the game prior is a shared pure function both import, so the two units never read each other (no cycle).

**Output, per car, compound and corner**, each value `Known` with a source tag `measured | profile | game | default`:
- the wear rate (% per lap) now;
- ν (lap-time loss per lap of age) and the loss per % of wear;
- the fresh-set offset against the medium;
- the laps to the 70 % limit, and the limit itself.

**Structure: one module per tyre type** (`slick`, `inter`, `wet`), each a small pure module with its own config and tests behind one interface; the unit owns what the types share (choosing the source, the limit, the as-of form). Improving one type's model touches only its module.

| Term | slick | inter | wet |
|---|---|---|---|
| Wear in age | linear (research 21 §2) | linear | linear |
| Measured rate | cumulative gain over the newest ≤ 5 green laps, from 3 gain laps and 5 % accrued at the corner (research 21 §2) | same | same |
| Prior before that | k × 70 / `usableLife` (research 22: AI k 0.86; a human's k from the profile, else the config default 1.3) | same | same |
| Drying term | none | rate × (1 + 0.06 per s of wetness lost) (research 21 §3) | none (not measured) |
| Heat term (user) | 0 %/lap per °C above the compound's reference temperature, source "not measured yet" | +0.042 %/lap per °C (research 20 §6) | 0, "not measured yet" |
| Lap-time loss | the game's loss per % (research 22 §1.6) × wear, plus the existing convex term above 40 % (flagged prior) | the game's loss per % | the game's loss per % |
| Fresh-set offset | the game's `lapDeltaMs` against a fresh medium; the track file only as fallback | the current config offsets (fitted with the wetness slopes; replaced only by a refit) | same as inter |

- **The heat term** applies to cars whose tyre temperatures the game simulates (our human cars, research 20 §1: AI temperatures are constants). The measured rate already contains the heat of its window; the term adjusts it by the difference between the carcass now and its mean over that window, and adjusts the game prior (which assumes the reference temperature) by the carcass now. Because the drying term is measured on AI cars (constant temperatures), the two never count the same effect.
- **The 70 % limit is a hard rule** (user): `tyre-model` gives the laps to it; `strategy-dp`, `race-monte-carlo`, `race-forecast`, `pit-window` and `rival-stops` never plan or predict a stint past it. `pit-window`'s latest stop is the limit; its best stop is the DP's.
- **Realism:** a rival's sets are hidden under realism (`state-update/realism.ts:22`); a rival's prior then comes from our own car's game values on that compound (research 22 §2).
- **Driver profiles:** the wear entry becomes the factor k per compound (`driverNoise.wearRatePct.<compound>` → a new key), scale-free across race distances (research 21 §13, 22 §1.3). No driver profile is stored yet (`PITWALL_DATA_DIR/drivers/` empty, 2026-11-14), so there is nothing to convert: the key is renamed and the old one removed; the drivers panel shows k.
- **O1a, the tyre facts (supervisor, step 3):** the projection carries every game tyre value a judgement needs, so the as-of forms (`forecast-score`, `tyre-model`'s and O9's past builds), calibration and profiles compute exactly what the live run computes (live state alone is not in the projection: `engine/src/calc/as-of.ts:147`). The lap record gains, per car and completed lap (supervisor's call: one change, one rules-version bump): the fitted set's `usableLifeLaps`; the `lapDeltaMs` of the best available fresh set per compound and per tyre type against the fitted set (the switch rule O5 and the fresh offsets); the `lapDeltaMs` of a fresh set of the fitted compound (the loss per % of wear); and, for cars whose temperatures the game simulates, the lap's mean carcass temperature per corner (the heat term). Values hidden under realism are `unknown('realism')` in the fact as in the live state (C8).
- **The game's loss per %** is computed from those facts (the fitted set against a fresh set of its compound, ÷ its wear), per car and compound, once the set has 8 % wear (below that the delta is noise); else the per-compound config defaults from research 22 §1.6 (C4 75, C3 57, C2 35, C1 22, inter 11 ms/%, source `default`), the wet's `default` equal to the inter's until measured.
- **Deletes:** `driver-noise`'s wear output and defaults (`humanWearRatePct`, `defaultWearRatePct`); `degradation`'s per-stint wear rate and its ν default as a model term (its filter prior comes from the shared prior function); `tyre-life`'s age basis, `ageLossLimitMs`, its fresh-life table and calibration wear entries (it becomes a reader of `tyre-model`); `forecast-field`'s ν, `minWearRatePctPerLap` and offset guesses; `stint-analysis/pool.ts`'s ν as a model term (the display's pool stays a display input); the per-car tyre terms in `StartingPoint`, `dp-input.ts` and `race-forecast/field.ts`; `shared/wear-rate.ts`'s median rule (fuel and ERS keep `per-lap-rate` and its `minSamples` 2; wear leaves it); the three worst-corner rules.

### 5.4 Strategy plans

- **`strategy-dp` returns base plans as SP4.3b §6 says:** the best per stop count (0–3) and compound sequence, **each with its own trigger thresholds** (SC/VSC range, damage, rain, degradation off); "box this lap" and "continue" are named outputs whose names say what they mean (T5: "not this lap" against "to the flag").
- **It plans over the weather worlds of O3's generator (§5.4a)**: one solve per world, each giving its base plans per stop count; the candidates are the union, tagged with their world; the Monte Carlo then scores every candidate over its own draws of the same generator. So the DP and the MC judge plans in the same weather (deferred item 11).
- **Per compound tyre terms from O1**, and no stint past the 70 % limit.
- **`strategy` selects, it does not edit:** candidates from named sources: base plans (always one per stop count; the R49 top-K bound applies within a stop count), stop-lap neighbours, rule families (mirror ahead and behind with the rival's lap **and compound**, deferred item 12; cover; extend), the committed policy. No candidate copies another's triggers.
- **`pitwall strategy --runs n`** overrides `n0` and `maxScenarioPolicies` for one call (T19).

### 5.4a The weather generator (supervisor's call)

One pure function owned by `track-wetness`: from the wetness state and the forecast it gives, for a uniform draw u, one weather path (wetness per remaining lap). It is today's `race-monte-carlo/weather.ts` model moved, unchanged in behaviour: it rains on a lap when u is below that lap's rain chance, the track wets and dries with the existing `WETNESS_RISE / FALL / MAX` dynamics from the current state (a wet track dries at that rate in a dry path), and the approximate-forecast shift stays. The Monte Carlo draws u per scenario as today, so its numbers do not change from the move. The DP solves the same function at K fixed draws (u at the K midpoint quantiles, weight 1/K each; K in `strategy-dp`'s config, default 2: one path at u = 0.25 and one at 0.75, i.e. a dry-leaning and a wet-leaning world of the forecast; more worlds cost 300 ms each). A forecast with no rain chance gives identical paths, and the DP solves once.

### 5.5 The restart (C59 as changed)

On a live session whose key (session uid, weekend id, player car) is already stored with a recording:
1. the bridge trims that `.pwrec` to its last complete record (a crash cuts it mid-record);
2. replays it into the new run's engine (the log is rebuilt, the run continues from the last frame);
3. appends the new packets after a **resume** record (a new record kind in `~/dev/personal/pitwall-recorder/FORMAT.md`, with the restart's wall time so record times stay non-decreasing; readers continue past it); the sidecars continue likewise (decisions at their record index, C76).

The continued run keeps the session's sidecars as they are: its effective config, priors snapshots, track file, driver profiles and realism stay those of the first run (C38, C47: fixed for the session), and decisions keep being appended at their record index (supervisor's call). Packets that arrive while the old recording replays are buffered in arrival order and written after the resume record, then applied, so the recording and the engine see the same sequence and reprocess equals the live run (C38). Task 27's "the newest run wins" (`storage-writer.ts` `startSession`) is replaced. The recorder repo's format doc and its reader change with it (aux repo, its own commit).

### 5.6 Tyre bands (`car-bands`)

- Carcass bands per actual compound: the reference temperature −20 … +15 °C (C1 85–120, C2 75–110, C3 70–105, C4 65–100, C5 60–95, inter 45–80, wet 35–70 °C; research 20 §7.1 A). An inter above 80 °C is out of band like every band (user).
- The pressure band derived from the carcass band: setup × (Tref − 20 + 273.15) / (Tref + 273.15) … setup × (Tref + 15 + 273.15) / (Tref + 273.15) (B).
- Wet surface band about 30–55 °C (C); slick and inter surface kept.
- Temperature and pressure bands judged only on human-driven cars (car driver, C17) (D).

### 5.9 Default workbooks reach the user

Live test 2026-11-14 (user): the garage workbook could not be opened and the strategy workbook was not the SP4.3b one. Cause (verified): `seedDefaultWorkbooks` (`apps/bridge/src/ui-state/default-workbooks.ts`) copies each default once and records its name; a file already there is kept, and a recorded name is never copied again. So a default updated in a later release never reaches a user who has the old file (the SP4.2 `strategy.json` stayed), and a default whose file disappeared stays gone (`garage.json` had been renamed to `garage.json.bak-4.1a` during SP4.1a). The user's folder was repaired by hand on 2026-11-14 (old strategy workbook kept as `strategy.json.bak-2026-11-14`).

The fix (bridge, UI state, C70, C72, C73):
- The marker records, per default, the content hash of the version seeded. At start, a default whose file still has the seeded hash (the user never changed it) is replaced by the new release's version, and its new hash recorded; a changed file is kept.
- A command "Reset workbook to default" (shell command registry, C72) sends a uiAction; the bridge replaces that workbook with the shipped default (keeping the old as a dated `.bak`) and publishes it (C73). The same for a deleted default: the palette lists defaults the folder lacks, as "Restore workbook".
- "A default the user deleted stays deleted" remains true for the automatic step; restoring is the user's command.

### 5.8 The guard

One completeness test per owner over the units' declared `reads` and imports: only the owner reads the raw source of its judgement (for example only `tyre-model` reads `tyres.sets` for rates; only `track-wetness` reads slick medians for a dry pace; only `shared/neutralised.ts` decodes neutralisation kinds). It fails when a second owner appears.
