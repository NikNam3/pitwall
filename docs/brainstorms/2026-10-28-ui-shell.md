## 1. What "clean UI" means for pitwall

**Base style: "quiet instrument".** Dark and almost grey-only, with dense, terminal-like tables. It's a tool, not artwork.

**Colour.** The user rejects "pick a palette and stick to it", which is tuned for an average user, not a high-quality tool. Colour is allowed for exactly two reasons:
1. **Highlight:** something wrong or very important. Colour always highlights, so anything the engineer doesn't need to look at right now stays grey.
2. **Distinction:** telling things apart, e.g. lines in a chart or table rows.

Rules derived from that, agreed:
- **Grey by default.** In-range values, idle values, text, borders and axes are neutral; a tyre in its window is grey.
- **Highlight colours** are saturated and few: critical, warning, and "very important / best".
- **Distinction must not highlight.** It uses lightness first: row banding is a lighter grey, not a hue. Chart series use muted colours of equal brightness, never the highlight hues.
- **Distinction colour is assigned per view,** so the series in one chart are as far apart as possible. There's no global car-colour palette.
- **F1 conventions decide *which* colour,** the user's rule decides *when*: purple = overall best, green = personal best, flag colours.
- **Undecided, to settle by mockups and live testing:** compound as a letter only, or letter plus colour; which personal-best sectors light up (own car only?).

**The two things that break a UI** (user's experience): bad colouring and widget rescaling. The code structure must handle both:
- **Colour lives in one place, in two layers:**
  - emphasis policy: pure functions decide *whether* something gets colour, e.g. `sectorEmphasis(sector, focus)`
  - theme: maps semantic roles to values
  - widgets only name roles; a lint rule bans colour literals outside the theme; open questions become theme variants you can switch at runtime
- **Rescaling: fixed type, content adapts.**
  - one type scale for the whole app; text never scales with the panel
  - widgets declare size modes and a priority per field, and the least important fields drop first
  - charts use extra space for more history, not thicker lines
  - one shared size primitive (`ResizeObserver`, device pixel ratio, declared minimum size); widgets never measure themselves
  - an in-app gallery renders every widget at fixed sizes with fixture data; Playwright screenshots of it catch regressions

**Typeface: JetBrains Mono, everywhere.** Labels, headers and chrome included; mixing fonts "looks ridiculous" (user).
- Iosevka (narrow mono) was rejected as hard to read.
- IBM Plex Mono looked identical to the user, and both are 0.6 em per character. JetBrains Mono won on symbol coverage (arrows, ±, °, Δ) and a single variable font file.
- Ligatures off. Bundled locally, with no internet dependency.
- Monospace makes "does this column fit" plain arithmetic.
- Mockups: `3-typeface.html`, `4-monospace.html`.

**Values that aren't simply there** (`Known`/`unknown(reason)`); mockup `5-value-states.html`:
- **Unknown or hidden** (no data yet, doesn't apply, private telemetry, realism mode): the **cell stays empty.** No dash, no "priv" label (user). The reason shows on hover.
- **Estimated by pitwall:** a `~` prefix plus a slightly dimmer grey.
- **Inactive car** (DNF, DSQ): a dim row with the reason, kept at the bottom so the order doesn't jump.
- **Stale:** the values stay but go dim, and the widget header shows `stale N s` in amber, once per widget.
- **Errored:** one sentence instead of numbers, red header; never old or invented numbers.

## 2. Context the user gave

- **League weekend:** either full (FP1–3, Q1–Q3, race) or short (one practice, short or one-shot qualifying, race), depending on the time available. Races are 50 % or 100 %, mostly 100 %.
- **No video:** the user does not watch the drivers' game, so both monitors are pitwall. They are a 24" main monitor and a 14" side monitor.
- **Attention in a race,** most important first:
  1. car care: calls to adjust the car, the job that always runs
  2. strategy
  3. race awareness
  4. coaching
  5. team play
- **Priority shifts with the race moment.** Near the tyre crossover, in the pit window, under SC/VSC, or after a crash, strategy dominates.
- **Strategy is about computed results,** not raw data: projected gains and losses, rejoin positions, undercut outcomes. Teams hide their tools, so pitwall may invent its own analyses or build on rumours, labelled as such. The goal: make the engineer's job as easy and as effective as possible.

## 3. Shell decisions

| Topic | Decision |
|---|---|
| Sub-project 2 scope | The shell only, plus one placeholder widget (feed/session status) to prove the path end to end. Real widgets come in sub-projects 3 and 4. Many mockups before code. |
| Layout behaviour | The layout stays stable; content escalates by colour when it starts to matter. Windows never move by themselves. |
| Workbook switching | Manual only: a key per workbook (e.g. `Ctrl+1`…`9`) plus a picker. No automatic switch at session change. |
| What a workbook is | One workbook covers all monitors. Each monitor is one browser window with a theme of its own (e.g. strategy, car). Call them **windows** in code, not "topics", which already means a bridge data stream. |
| Car selection | ATLAS-style **link groups.** A group carries the primary car (default: my driver), compare cars, and a time window (lap or range, like ATLAS's timebase). Each widget follows a group or keeps its own selection. Group 1 by default, so out of the box it acts like one global selection. Groups are marked with numbers, not colours. |
| Fixed top bar | Not dockable, always visible: session, lap, clock, flag state, feed health, alerts. |
| Alerts (MVP) | Tier-1 alerts stay listed in the top bar until acknowledged (one key for all, or one at a time). The widget highlight stays while the condition holds. ATLAS-style groups (tyres, fuel/ERS, strategy, feed, …) can be muted. **Sound later,** not in the MVP. |
| Where UI state lives | **The bridge owns it.** Workbooks are hand-editable JSON files in `PITWALL_DATA_DIR`. Each window is a normal client; workbook switches, link-group changes and acknowledgements go through the bridge, which tells every window. |
| Default race layout | **Tentative:** strategy and simulations on the main 24", car information on the 14". The final layout follows from research 06. Mockup `2-race-layout.html` shows earlier options (A car centre, B three columns, C split by time). The user didn't choose, because the content depends on the catalogue. |

## 4. Design section 1 (drafted, not approved)

Presented once, then paused before the user replied. Re-present it after reconciling with research 06.

- **Sub-project 2 delivers:**
  - the visual system (theme, type, value states)
  - windows and workbooks with docking, the fixed top bar with alerts, link groups
  - the bridge connection, the widget contract with the size primitive, the gallery
  - one placeholder widget
- **Folders in `apps/ui/src/`:**

  | Folder | Job |
  |---|---|
  | `connection/` | WebSocket client, topic store (one shared fold for snapshot/update/append), reconnect, `hello` version check |
  | `shell/` | windows, workbook switching, docking (thin adapter over dockview-core), fixed top bar, keyboard |
  | `theme/` | semantic colour roles → values, theme variants, type scale; the only place colour values exist |
  | `emphasis/` | pure functions deciding whether something gets colour; no Svelte, unit-tested |
  | `layout/` | size primitive, priority-based field dropping, canvas surface |
  | `values/` | one component that renders any `Known` value |
  | `widgets/<name>/register.ts` | one folder per widget, found by convention via a generated index (ADR 0005) |
  | `gallery/` | every widget at fixed sizes with fixture data, plus a theme-variant switcher |

- **UI state as bridge topics:** `ui.workbooks`, `ui.linkGroups`, `ui.alerts` (acknowledged, muted). Changes go through one new client message, `uiAction`, and are persisted in `PITWALL_DATA_DIR/ui/`. These are `contracts` changes, so they are supervisor-owned.
- **Enforced:** dependency-cruiser (`ui` imports only `contracts` and `domain`), no colour literals outside `theme/`, no font other than JetBrains Mono.

Still to present: the visual system in detail (type scale, density), the shell, the widget contract, data flow, alerts, gallery and testing.

## 6. Reconcile with research 06 before continuing

- **Numbers only, no verdicts** (06, 1.3 and section 5).
  - The race-layout mockup's strategy text ("Window open · box L24 → P7") is partly a verdict.

- **Display catalogue V01–V35 and the escalation map** in 06 replace the inventory's "strategy decisions (computed)" group as the content basis. The inventory tiers still hold for the raw data.
